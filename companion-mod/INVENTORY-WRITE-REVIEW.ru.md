# Проверка записи инвентаря 7DTD — 2026-09-20

Статус: исследование завершено для перечисленных механизмов. Запись выбранного
слота онлайн-игрока НЕ включена. Это не доказательство отсутствия любого другого
способа; проверенные API не обеспечивают требуемую синхронизацию и подтверждение.

## Результаты

1. `NetPackagePlayerInventory.PackageDirection = ToServer` в серверной и клиентской
   DLL. `ProcessPackage` заменяет поля `Sender.latestPlayerData` и отмечает снимок
   изменённым. Это клиентский снимок для сервера, не команда записи слота клиенту.
   `NetPackagePlayerData` также направлен ToServer. Правка latestPlayerData на сервере
   может быть затёрта следующим снимком клиента.

2. `NetPackageInventoryTransactionResponse.ProcessPackage` пуст даже в проверенной
   клиентской DLL. `InventoryManager.TransactionResponse` бросает NotImplementedException.
   Поэтому нельзя объяснять пустой обработчик только урезанием dedicated-сборки.

3. `NetPackageInventoryDataResponse` обновляет зарегистрированный TransactionalInventory
   по GUID. `InventoryManager.ReadInventory/WriteInventory` работают с режимами
   TileEntity. Проверенного соответствия этого GUID обычному поясу/рюкзаку игрока
   не найдено. Создание отдельного TransactionalInventory не делает его рюкзаком.

4. `NetPackagePlayerEquipment` применяет Equipment и распространяет изменение другим
   клиентам. Это не универсальный пакет для рюкзака; нет проверенной защиты выбранного
   слота от устаревшего состояния и подтверждения владельца.

5. ServerKit `Commands/RemovePlayerItems.cs` и `Hooks/WorldStaticDataHook.cs` добавляют
   уникальные теги предметам и последовательности игровых событий. Онлайн-удаление
   вызывает RemoveItems по тегу для Toolbelt,Backpack, без номера слота и без свойства
   count в сгенерированном событии. Нельзя выдавать эту операцию за удаление одного
   выбранного стака. В офлайн-ветке ServerKit меняет PlayerDataFile и сохраняет файл.

6. Клиентский `GameEvent.SequenceActions.ActionBaseItemAction` перебирает секции и
   слоты. `ActionRemoveItems` фильтрует по тегам и количеству, а не по ожидаемому
   содержимому конкретного слота. Ограничение count не гарантирует выбор нужного
   экземпляра с нужным качеством/модификациями. Отправка Approved-события сама по себе
   не подтверждает удаление и не даёт безопасного повтора после таймаута.

## Решение и варианты продолжения

В 1.0.11 добавлен ограниченный офлайн-редактор количества стаков пояса/рюкзака.
Онлайн-редактирование не включено. Зависимости, фоновые задачи и изменения GC не добавлялись.

Выбор владельца от 2026-09-20: сначала офлайн-просмотр, затем безопасная запись.
Офлайн-просмотр 1.0.10 и выдача подтверждены владельцем на сервере. Запись 1.0.11
требует отдельного живого теста. Дополнительная проверка DLL установила:

- `ConnectionManager.DisconnectClient` переводит вызов в main thread, вызывает
  PlayerDisconnected ДО последнего синхронного Save и удаляет ClientInfo ПОСЛЕ Save.
- Вход через NetPackageRequestToSpawnPlayer/RequestToSpawnPlayer и пакеты сохранения
  обрабатываются ConnectionManager.Update/ProcessPackages в главном потоке.
- `PlayerDataFile.Save` проглатывает исключения и копирует `.tmp` поверх основного
  файла; потому не используется как транзакционное API. Native Write сериализует
  в память; исходный round-trip обязан совпасть. Замена — File.Replace с копией.

Текущая транзакция полностью выполняется в одном callback main thread, включая
короткий I/O (до 1 MiB); это не даёт нативному входу/сохранению вклиниться между
проверкой и commit, без Harmony. Не распространять этот вывод на сторонние моды,
которые записывают player-файлы из своих потоков. Нужен замер на реальном сохранении.
Остальные ограничения и альтернативы:

- **Офлайн-редактор точного слота**: отдельно спроектировать запрет входа на время
  операции, ожидание завершения сохранения после выхода, резервную копию конкретного
  player-файла, сравнение его ревизии, восстановление при сбое. Не принуждать игрока
  к выходу скрыто и не считать одиночную проверку offline достаточной защитой.
  Сначала read-only просмотр офлайн-файла, потом запись.
- **Ограниченная онлайн-конфискация по типу**: явно назвать действие, показать область
  удаления и число затрагиваемых вещей; отдельно проверить передачу игровых событий,
  совместимость XML/тегов, подтверждение результата и таймауты. Это не слот-редактор.
- **Точный онлайн-редактор**: дальнейший поиск штатного подтверждаемого механизма;
  если потребуется клиентское расширение, сначала пересогласовать требование
  «игроки ничего не устанавливают». Один лишь клиентский мод у админа не исправляет
  синхронизацию инвентаря другого игрока с ванильным клиентом.

Дальнейшая дорожная карта: проверка уменьшения/удаления 1.0.11 → расширение офлайн-редактора →
история игроков → телепортация/наборы/зоны → автоматизация. Виртуальная экономика
исключена: достаточно штатной торговли фишками, улучшения обсудим отдельно.
Выдача и офлайн-просмотр подтверждены владельцем; не приравнивать это к проверке записи.
