# Экосистема плагинов Aurum: разбор и план

Разбор предложения из `CLAUDE.md` (контекст для трёх новых плагинов) применительно
к тому, что реально лежит в репозитории. Кода этот документ не меняет — он
объясняет, что уже есть, где плагины действительно пересекаются, с чем в
предложении я согласен, а где оно недоговаривает, и в каком порядке это делать
на **живом сервере с игроками**.

## Что уже есть

Шесть плагинов, три из которых приехали недавно:

| Плагин | Где | Сборка | Java | API сервера | Пакет |
| --- | --- | --- | --- | --- | --- |
| AurumAuth | `auth-plugin/` | Gradle, 4 модуля | api/core 21, paper 25 | paper-api 26.2 | `ovh.aurumgg.auth` |
| AurumGuilds | `guilds-plugin/` | Gradle, 3 модуля | api/core 21, paper 25 | paper-api 26.2 | `ovh.aurumgg.guilds` |
| AurumCompanion | `companion-plugin/` | Gradle, 2 модуля | core 21, paper 25 | paper-api 26.2 | `ovh.aurumgg.companion` |
| AddonsNPC 1.5.3 | `other-plugins/AddonsNPC/` | Maven, 1 модуль | 25 | **spigot-api** 26.2 | `dev.addons.npc` |
| AurumArena 1.1.5 | `other-plugins/AurumArena/` | Maven, 1 модуль | 25 | paper-api 26.2 | `org.ChisaO_o.gladiatorArena` |
| AurumSlots 1.1.2 | `other-plugins/AurumSlots/` | Maven, 1 модуль | 25 | paper-api 26.2 | `org.ChisaO_o.simpleSlots` |

Все три новых плагина здесь собраны и прогнаны: AddonsNPC — 28 тестов,
AurumArena — 16, AurumSlots — 8, все зелёные, jar-ы получаются.

Два различия между «нашими» и «новыми», которые дальше будут мешать:

- **Ядро без Bukkit.** У Auth, Guilds и Companion вся логика, которую можно
  проверить без сервера, вынесена в модуль `core` на Java 21, а Bukkit-адаптер
  лежит отдельно. У трёх новых логика живёт прямо в Bukkit-классах:
  `GladiatorArena.java` — 1308 строк, `NpcCommand.java` — 1345, `SimpleSlots.java`
  — 815. Тесты там есть, но они проверяют разбор конфигов и модели, а не
  сценарии боя, покупки и спина.
- **AddonsNPC собран против spigot-api, а не paper-api.** Это осознанно (Paper-only
  вещи изолированы в `MannequinAdapter`), но означает, что часть Paper API ему
  просто не видна на компиляции.

## С чем в предложении я согласен

- **Не делать сразу один обязательный плагин.** Разделение на «контракты →
  библиотеки времени сборки → опциональный рантайм-Core» — правильное. Монолит
  превратил бы падение любой части в падение всех.
- **Один владелец API-класса в рантайме.** Провайдер содержит и регистрирует
  API, потребитель берёт `compileOnly` и не шейдит его к себе. Это ровно то,
  как сейчас устроены `auth-api` и `guilds-api`, и ломать это нельзя.
- **ServicesManager для поиска, `softdepend` для необязательных связей,
  `depend` — только когда без провайдера плагин неверен.** Так уже работают
  наши интеграции с Vault, LuckPerms, WorldGuard и InvSee++.
- **Не тащить AurumAuth в рантайм-Core.** Вход должен работать, когда всё
  остальное лежит. Это единственная критичная для входа на сервер система.
- **Не объединять пулы БД, пока не измерено.** Общий пул экономит соединения,
  но всплеск в арене начинает конкурировать с аутентификацией. Сначала общий
  код конфигурации и миграций, соединения — потом и по замерам.
- **Никогда не проверять жизненный цикл через `/reload`.** Проверка — чистый
  старт, чистая остановка, полный рестарт.

## Что нашлось в коде

Пять находок. Это не пересказ предложения, это то, что видно в файлах.

### 1. Провайдер Vault кэшируется в поле — у всех трёх новых плагинов

- `AddonsNPC/…/service/EconomyService.java`: поле `economy`, заполняется один раз в `setup()`.
- `AurumArena/…/GladiatorArena.java`: поля `economy` и `vaultReady`, заполняются на старте.
- `AurumSlots/…/SimpleSlots.java`: поле `economy`, заполняется на старте.

Наш `guilds-plugin/paper/…/VaultBridge.java` так не делает и объясняет почему:
Vault денег не хранит, это шина, а провайдера за ней регистрирует **третий**
плагин (EssentialsX, CMI — какой именно, мы не знаем и в `softdepend` его не
пропишем). Его `onEnable` вполне может пройти позже нашего, а перезагрузка
плагина экономики на живом сервере оставляет ссылку на мёртвый экземпляр.
Поэтому провайдер спрашивается у `ServicesManager` на каждом обращении.

Это не стилистическая разница. У трёх новых плагинов после перезагрузки плагина
экономики выплаты тихо перестают работать, и в консоли об этом ничего не будет.
Самый весомый аргумент за общую библиотеку — не «меньше дублей», а «одна
правильная реализация вместо трёх неправильных».

### 2. Рефлексия в AddonsNPC ложится на `guilds-api` один в один

`AddonsNPC/…/service/AurumGuildsHook.java` — 171 строка, которая по именам ищет
класс `ovh.aurumgg.guilds.api.AurumGuildsApi` в `ServicesManager` и дёргает
методы через `getMethod(...).invoke(...)`.

Всё, что он дёргает, в нашем API есть с теми же сигнатурами:

| Что дёргает хук | Что есть в `guilds-api` |
| --- | --- |
| `membership(UUID)` → `guildId`/`guildName`/`guildTag`/`rank` | `Optional<GuildMembership> membership(UUID)` |
| `bonuses(long)` → `type`/`magnitude`/`expiresAt`/`grantedBy` | `List<GuildBonus> bonuses(long)` |
| `grantBonus(long, BonusType, double, Duration, String)` | она же, возвращает `CompletableFuture<GuildActionResult>` |
| `ok`/`message` у результата | поля `GuildActionResult` |
| `weight` у ранга | `GuildRank.weight()` |

Замена механическая. Выигрыш не в строках, а в том, что дрейф API становится
ошибкой компиляции, а не предупреждением в консоли через месяц после того, как
трейдер перестал работать.

### 3. Три независимые реализации владения дисплеями

Логика «заспавнить `TextDisplay`, пометить своим ключом в PDC, найти рядом
только свои, удалить только свои» написана трижды:

| Плагин | Ключи |
| --- | --- |
| AurumArena | `gladiatorarena:hologram` |
| AurumSlots | `simpleslots:hologram`, `simpleslots:hologram_machine` |
| AddonsNPC | `npc-id`, `npc-label-id` (через `new NamespacedKey(plugin, …)`) |

Кандидат в общую библиотеку — да. Но с жёсткой оговоркой: **ключи менять
нельзя**. По ним находятся голограммы, уже стоящие в мире. Общая утилита должна
принимать ключ снаружи, а не назначать свой.

### 4. Кросс-плагинный денежный путь уже существует ровно один

`AddonsNPC/…/service/GuildTraderService.java`: игрок покупает бонус гильдии у
NPC. Деньги списываются через Vault, затем через рефлексию вызывается
`AurumGuilds.grantBonus`, и при отказе платёж возвращается — возврат аккуратно
завёрнут в `runTask`, то есть выполняется в основном потоке.

Написано это правильно. Но там же есть честная строка:

> `plugin.getLogger().severe("Guild bonus transaction completed while AddonsNPC was disabled for " + playerId + "; verify the payment and bonus manually.")`

То есть если сервер остановился между списанием и ответом гильдий — деньги
списаны, а выдан бонус или нет, узнать некому. Сейчас это строка в логе. Это и
есть тот случай, ради которого в предложении заведён леджер: превратить её в
восстановимую запись. Один конкретный сценарий, а не абстракция.

### 5. Панель трёх новых плагинов не видит вовсе

У companion сейчас маршруты `players`, `players/known`, `players/{uuid}/ips`,
`inventory`, `permissions`, `economy`, `guilds`, `plugins`, `webtoken`,
`complete`, `auth` и шесть интеграций (Auth, Guilds, Vault, LuckPerms,
Essentials, InvSee++). Ни арен, ни автоматов, ни NPC там нет.

В панели `KNOWN_PLUGINS` (`packages/shared/src/modules/minecraft.ts`) перечислены
шесть плагинов — AddonsNPC, AurumArena и AurumSlots среди них тоже нет. То есть
даже в списке «что стоит на сервере» они не отображаются.

## Что предложение недоговаривает

**а) `aurum-common` шейдится в каждый плагин, а значит правка библиотеки — это
пересборка и замена всех пяти jar-ов разом.**

Предложение говорит «shaded and relocated into each consuming plugin» и на этом
останавливается. Практическое следствие надо сказать вслух: обновление общей
библиотеки на живом сервере — это не «положил один файл», а «остановил сервер,
положил пять файлов, поднял». Соблазн «поправлю в common, разложу потом»
приведёт к серверу, где в разных jar-ах лежат разные версии одного класса, и
поведение зависит от того, чей класслоадер ответил первым. Отсюда правило:
общая библиотека версионируется, и в каждом релизе фиксируется, какая версия
внутри какого jar-а.

**б) Публикация в настоящий Maven-репозиторий на этом этапе избыточна.**

Шаг 1 предложения — «Publish the existing Auth and Guilds APIs as versioned
Maven artifacts, add a BOM». Для одного человека с одним сервером это обвес,
который придётся обслуживать. Достаточно `maven-publish` в файловый репозиторий
внутри репозитория (например `libs/`) плюс `publishToMavenLocal` — Maven-сборки
трёх плагинов возьмут артефакт оттуда, а компиляция останется
воспроизводимой. Настоящий репозиторий и BOM нужны, когда артефакты потребляет
кто-то за пределами этой машины.

**в) Леджер транзакций — самая ценная часть предложения и самая опасная.**

Он встраивается в денежные пути на сервере, где прямо сейчас играют. Я бы делал
его **последним**, и первый релиз — в режиме наблюдения: пишет запись, но
решения не меняет и отказ журнала не отменяет операцию. Только когда в журнале
за пару недель накопится картина и станет видно, что он ничего не ломает,
включать идемпотентность и восстановление. Обратный порядок — это способ
получить «деньги списались, а предмет не выдался» руками той самой системы,
которую делали, чтобы этого не было.

**г) Данные, которые нельзя трогать, стоит перечислить явно.**

Предложение говорит общее «не переименовывать без моста». Конкретно в этих
плагинах нельзя трогать:

- PDC-ключи `gladiatorarena:*`, `simpleslots:*`, `npc-id`, `npc-label-id` —
  по ним находятся сущности, уже стоящие в мире;
- таблицу `gladiator_stats` и `recovery.yml` арены — там незавершённые матчи и
  сохранённые инвентари;
- пути в `config.yml`, `npcs.yml`, `shops.yml`, `buyers.yml`, `guild-traders.yml`;
- плейсхолдеры `aurumarena_*` и легаси `gladiatorarena_*`;
- имена команд и прав.

Пакеты `org.ChisaO_o.*` и `dev.addons.npc` при этом переименовывать в
`ovh.aurumgg.*` не нужно вовсе: снаружи они не видны, а риск — реальный.
Единообразие имён пакетов не стоит ни одной потерянной голограммы.

## План

Шаги независимы настолько, насколько это возможно: каждый можно остановить
после, ничего не ломая. Порядок выбран от «видно сразу, риск нулевой» к «ценно,
но трогает деньги».

### Шаг 0. Проверяемая сборка всех шести — 1 подход

Сейчас Gradle-плагины собираются одной командой, Maven-плагины — тремя
другими. Свести к одному скрипту (`deploy/build-plugins.sh` или задача Gradle,
вызывающая `mvn`), который собирает всё и прогоняет все тесты. Без этого любое
изменение в общем коде проверяется вручную и рано или поздно не проверяется.

*Риск: нулевой, ничего не выполняется на сервере.*

### Шаг 1. `guilds-api` доступен Maven-сборкам — 1 подход

Добавить в `guilds-plugin` `maven-publish`, публиковать `guilds-api` в файловый
репозиторий внутри репы. То же для `auth-api` — он понадобится позже.

*Риск: нулевой, jar плагинов не меняется.*

### Шаг 2. AddonsNPC: рефлексия → `compileOnly guilds-api` — 1 подход

Заменить `AurumGuildsHook` типизированным вызовом. `ServicesManager` остаётся,
проверка «плагин есть?» остаётся, `softdepend` остаётся, поведение без
AurumGuilds не меняется. Уходит 171 строка рефлексии.

Проверять обязательно **оба** состояния: с установленным AurumGuilds и без
него. Второе — не формальность: типизированная ссылка на отсутствующий класс
падает иначе, чем рефлексия.

*Риск: низкий. Трогается один плагин, поведение проверяемо на тестовом сервере.
Откат — вернуть старый jar.*

### Шаг 3. Общая работа с Vault — 2 подхода

Вынести в `aurum-common-paper` резолв провайдера (по образцу нашего
`VaultBridge`: спрашивать каждый раз, проверять `isEnabled()`, ловить
`NoClassDefFoundError`) и проверенный результат транзакции. Подключить в
AddonsNPC, AurumArena, AurumSlots, Guilds и Companion.

Это чинит находку №1 — не рефакторинг ради чистоты, а исправление тихой
поломки выплат после перезагрузки плагина экономики.

*Риск: средний, трогает денежные пути во всех пяти. Обязательно: замер до и
после, проверка на тестовом сервере с перезагрузкой EssentialsX на живую.*

### Шаг 4. Общая работа с дисплеями — 1 подход

Вынести создание `TextDisplay` с меткой владельца, дальность видимости,
непрозрачность стен, дедупликацию и удаление только своих. **Ключи PDC каждый
плагин передаёт свои** — общая утилита их не назначает.

*Риск: низкий по данным, средний по внешнему виду. Проверять глазами на
тестовом мире: голограммы арены, автоматов и подписи NPC.*

### Шаг 5. Панель видит арены, автоматы и NPC — 2–3 подхода

Companion получает маршруты только на чтение: список арен с состоянием, список
автоматов, список NPC. Плюс три записи в `KNOWN_PLUGINS`, чтобы панель хотя бы
показывала, что они установлены.

Читать данные companion может двумя способами: через Java API этих плагинов
(которого у них пока нет) или через их же YAML-файлы. Первый правильнее, второй
дешевле; начинать стоит с минимального read-only API у каждого из трёх.

*Риск: низкий — только чтение. Но помнить про урок `/economy`: не перебирать
всех офлайн-игроков и не ходить в главный поток без кэша и таймаута.*

### Шаг 6. Остальное общее — по мере надобности

Разбор длительностей, денег, цветов; валидация и версионирование конфигов;
именованные ограниченные пулы потоков; сборка конфигурации Hikari и запуск
миграций; парсеры аргументов и автодополнение команд. Выносить **только то, что
уже понадобилось минимум двум плагинам** — иначе общая библиотека превращается
в свалку.

### Шаг 7. Леджер и `/aurum doctor` — отдельный разговор

`AurumCore` с журналом операций «только на добавление», ключами
идемпотентности и восстановлением зависших платежей. Источники: `npc.shop.purchase`,
`npc.buyer.sale`, `npc.guild_bonus`, `arena.bet`, `arena.payout`, `slots.bet`,
`slots.win`.

Порядок внутри шага: сначала журнал в режиме наблюдения, потом одна операция с
идемпотентностью (лучше всего `npc.guild_bonus` — там уже есть возврат и уже
есть та самая строка в логе про ручную проверку), потом остальные.

*Риск: высокий. Делать последним, на живой сервер — только после того, как
режим наблюдения отработал без замечаний.*

## Чего делать не стоит

- **Переименовывать пакеты и ключи ради единообразия.** Снаружи их не видно, а
  сломать можно данные в мире.
- **Объединять базы и пулы соединений до замеров.** Всплеск в арене не должен
  мешать входу на сервер.
- **Тащить AurumAuth в общий рантайм-Core.** Вход должен работать, когда лежит
  всё остальное.
- **Переводить три плагина на Gradle сейчас.** Это переписывание трёх `pom.xml`
  вместе с shade-конфигурацией арены, ради удобства, которое шаг 1 закрывает
  дешевле.
- **Считать перенос кода улучшением производительности.** Пока не измерено — это
  просто перенос кода.
