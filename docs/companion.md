# Companion-плагин: подробная установка

Модуль Minecraft работает и **без** этого плагина: игроки, кик, бан, whitelist
и команды идут через RCON. Плагин закрывает два пробела, которые RCON закрыть
не может, и работает в две стороны:

```
   панель  ──── HTTP + токен ────►  плагин      список игроков, инвентарь
 10.0.0.1                          10.0.0.2

   панель  ◄─── HTTP + токен ────   плагин      /ticket от игрока
```

| Возможность | Без плагина | С плагином |
| --- | --- | --- |
| Список игроков | только ники | + UUID, пинг, здоровье, мир, координаты |
| Аватары | две буквы в квадратике | настоящий скин через Crafatar |
| Инвентарь игрока | недоступен | сетка предметов, броня, вторая рука, зачарования |
| Обращение игрока | никак | команда `/ticket <сообщение>` прямо в игре |
| Ответ модератора | только в панели | приходит игроку в чат |

**Ставить необязательно.** Если сейчас не хочется — пропустите, панель
работает и так, а вкладка «Инвентарь» покажет ссылку на эту страницу.

---

## Что понадобится

- Доступ в Pterodactyl под администратором.
- Машина, где можно собрать `.jar` — подойдёт ваш компьютер или VDS.
- 30–40 минут.

Порядок такой: **собрать jar → выделить порт → залить файл → настроить →
прописать в панели**.

---

## Часть 1. Собрать .jar

Сборку можно делать где угодно — хоть на своём ноутбуке, хоть на VDS.
Готовый файл потом просто загрузите через браузер.

### 1.1. Проверить Java

**Собираете на Windows?** Отдельная пошаговая инструкция:
[`companion-plugin/BUILD-WINDOWS.md`](../companion-plugin/BUILD-WINDOWS.md).
Дальше здесь — про Linux и macOS.

Gradle ставить не нужно: в репозитории лежит обёртка `gradlew`, она скачает
нужную версию сама.

Модуль `paper` компилируется **JDK 25** — Paper 26.x собран под него, и
компилятор постарше не прочитает его class-файлы. Но качать этот JDK вручную
не обязательно: в `settings.gradle.kts` подключён резолвер тулчейнов, и
Gradle достанет JDK 25 сам. Достаточно, чтобы в системе была любая Java 17+,
на которой запустится сама сборка:

```bash
java -version
```

Если Java нет вовсе:

```bash
sudo apt-get install -y openjdk-21-jdk-headless
```

<details>
<summary>Если Gradle не смог скачать JDK 25 сам (нет интернета, мешает прокси)</summary>

Поставьте JDK 25 вручную из Adoptium — это официальная сборка OpenJDK от
Eclipse Foundation:

```bash
sudo apt-get install -y wget apt-transport-https gpg

wget -qO - https://packages.adoptium.net/artifactory/api/gpg/key/public \
  | sudo gpg --dearmor -o /etc/apt/keyrings/adoptium.gpg

echo "deb [signed-by=/etc/apt/keyrings/adoptium.gpg] https://packages.adoptium.net/artifactory/deb $(awk -F= '/^VERSION_CODENAME/{print$2}' /etc/os-release) main" \
  | sudo tee /etc/apt/sources.list.d/adoptium.list

sudo apt-get update
sudo apt-get install -y temurin-25-jdk
```

На Ubuntu 24.04 подойдёт и штатный пакет: `sudo apt-get install -y openjdk-25-jdk-headless`.

Если пакет не находится — есть [SDKMAN](https://sdkman.io/)
(`sdk install java 25-tem`) или архив с [adoptium.net](https://adoptium.net/).

Проверить, какие Java видит сборка:

```bash
./gradlew -q javaToolchains
```

В списке должна быть запись `Language Version: 25`.

</details>

### 1.2. Собрать

```bash
cd /opt/aurum-panel/companion-plugin      # или туда, куда склонировали репозиторий
./gradlew :paper:jar
```

Первый запуск качает Gradle и зависимости — **3–5 минут**, дальше быстрее.

Ожидаемо в конце: `BUILD SUCCESSFUL`.

Готовый файл:

```bash
ls -lh paper/build/libs/
```

Ожидаемо: `AurumCompanion-0.1.0.jar`, размер порядка 30–60 КБ.

### Если не получилось

- **`Cannot find a Java installation … matching {languageVersion=25}`** →
  Gradle не нашёл JDK 25 и не смог его скачать. Поставьте вручную —
  см. развёрнутый блок в шаге 1.1.
- **`error: invalid source release: 25`** → сборка взяла старую Java.
  Посмотрите `./gradlew -q javaToolchains`: в списке должна быть 25.
- **`Could not resolve io.papermc.paper:paper-api`** → нет доступа к
  `repo.papermc.io`. Проверьте интернет и что не мешает корпоративный прокси.
- **`Cannot select module with conflict on capability 'org.bukkit:bukkit'`** →
  это уже починено в `paper/build.gradle.kts`, и если ошибка всё же вылезла,
  значит собирается старая версия файла — обновите репозиторий.

  Суть: VaultAPI тянет за собой `org.bukkit:bukkit` восьмилетней давности
  (JitPack пересобирает его и публикует свой pom, где эта зависимость
  попадает в compile), а `paper-api` объявляет собой ту же способность
  (`capability`) — Paper делает это нарочно, чтобы старый Bukkit и Paper не
  встретились в одном classpath. Gradle видит двух поставщиков одного и того
  же и отказывается выбирать.
  Лечится исключением старого Bukkit из VaultAPI: все классы `org.bukkit.*`
  даёт `paper-api`, он их надмножество.

  ```kotlin
  compileOnly("com.github.MilkBowl:VaultAPI:1.7") {
      exclude(group = "org.bukkit", module = "bukkit")
  }
  ```

  Если когда-нибудь добавите ещё одну библиотеку эпохи Bukkit и увидите ту же
  ошибку — лечится так же, исключением в её объявлении.
- **`Permission denied: ./gradlew`** → `chmod +x gradlew` и повторите.
- **Не хочется возиться со сборкой** → соберите на своём компьютере (шаги те
  же) и загрузите готовый jar через браузер на шаге 3.

## Часть 2. Выделить порт плагину в Pterodactyl

Плагин поднимает свой маленький HTTP-сервер, и ему нужен порт. В Pterodactyl
порты выдаются через **allocations**.

> ⚠️ Порт плагина так же чувствителен, как RCON: кто до него дотянется,
> увидит инвентари игроков. Он должен смотреть только в туннель.

### 2.1. Создать allocation

1. Откройте `https://panel.aurumgg.ovh` под администратором.
2. Значок гаечного ключа (админка) → левое меню **Nodes** → выберите ваш узел.
3. Вкладка **Allocation**.
4. В форме создания:
   - **IP Address**: `10.0.0.2` — адрес туннеля, **не публичный IP**
   - **Ports**: `8085` (для второго сервера потом `8086` и так далее)
5. Нажмите **Submit**.

Если в выпадающем списке IP нет `10.0.0.2` — сначала добавьте его как
дополнительный IP узла в поле выше на той же вкладке.

### 2.2. Выдать allocation серверу

1. Админка → **Servers** → выберите нужный сервер.
2. Вкладка **Build Configuration**.
3. Блок **Additional Allocations** → выберите созданный `10.0.0.2:8085`.
4. **Update Build Configuration**.

### Что должно получиться

На странице сервера в разделе Network появился второй адрес `10.0.0.2:8085`
рядом с основным игровым портом.

### Если не получилось

- **В списке нет `10.0.0.2`** → allocation создан на другом IP. Вернитесь
  к 2.1 и убедитесь, что выбран именно адрес туннеля.
- **Allocation занят другим сервером** → возьмите следующий свободный порт.

## Часть 3. Залить jar на сервер

Два способа — выберите любой.

### Способ А: через браузер (проще)

1. Откройте сервер в Pterodactyl → вкладка **Files**.
2. Зайдите в папку **plugins** (если её нет — создайте кнопкой **New Folder**).
3. Кнопка **Upload** вверху справа.
4. Выберите `AurumCompanion-0.1.0.jar`.

### Способ Б: через SFTP (удобнее, если файлов много)

1. В Pterodactyl откройте сервер → **Settings** → блок **SFTP Details**.
   Там указаны адрес, порт и логин.
2. Пароль — **тот же, что от вашей учётки Pterodactyl**.
3. Подключитесь любым SFTP-клиентом (FileZilla, WinSCP) или из терминала:

```bash
sftp -P <порт-из-SFTP-Details> <логин-из-SFTP-Details>@<адрес-из-SFTP-Details>
cd plugins
put AurumCompanion-0.1.0.jar
exit
```

### 3.1. Первый запуск — создаст конфиг

Перезапустите сервер кнопкой **Restart** в Pterodactyl.

В консоли сервера должна появиться строка вроде:

```
[AurumCompanion] HTTP-сервер не запущен: в config.yml не задан token
```

**Так и должно быть** на первом запуске: плагин загрузился, создал конфиг и
намеренно не поднял HTTP-сервер, потому что токен ещё не задан. Это защита от
случайного выхода в сеть с предсказуемым секретом.

### Если не получилось

- **В консоли ничего про AurumCompanion** → jar лежит не в `plugins/`
  или сервер не Paper/Spigot (на ванильном сервере плагины не работают).
- **`Unsupported class file major version`** → jar собран старой Java.
  Вернитесь к 1.1 и пересоберите на JDK 25.

## Часть 4. Настроить плагин

### 4.1. Сгенерировать токен

Выполните на любой машине:

```bash
openssl rand -base64 32
```

**Сохраните вывод в менеджер паролей** — этот же токен вводится и в панели.

> ⚠️ Токен должен состоять только из латиницы, цифр и знаков препинания.
> Вывод `openssl rand -base64 32` подходит. **Кириллицу использовать нельзя** —
> токен передаётся в HTTP-заголовке, а заголовки не принимают не-ASCII символы.
> Плагин это проверяет и откажется стартовать с понятным сообщением.

### 4.2. Узнать ID сервера в панели

Откройте вашу новую панель `https://manage.aurumgg.ovh`, зайдите на страницу
нужного сервера и посмотрите на адресную строку:

```
https://manage.aurumgg.ovh/servers/65f3a52c-2c20-4006-b8be-dccbb5471546
                                    └────────── это и есть ID ──────────┘
```

Скопируйте эту часть.

### 4.3. Заполнить config.yml

В Pterodactyl: сервер → **Files** → папка `plugins/AurumCompanion/` → файл
`config.yml` → щёлкните по нему, откроется редактор.

Приведите файл к такому виду:

```yaml
token: СЮДА_ТОКЕН_ИЗ_ШАГА_4.1

http:
  bind: "0.0.0.0"
  port: 8085

panel:
  base-url: "http://10.0.0.1:3001"
  server-id: "СЮДА_ID_ИЗ_ШАГА_4.2"

tickets:
  cooldown-seconds: 10
```

Пояснения к полям:

| Поле | Что означает |
| --- | --- |
| `token` | общий секрет: им панель входит в плагин, а плагин — в панель |
| `http.bind` | `0.0.0.0` — внутри контейнера так и надо; наружу порт выпускает allocation |
| `http.port` | **должен совпадать** с портом allocation из части 2 |
| `panel.base-url` | внутренний адрес панели через туннель, **не публичный домен** |
| `panel.server-id` | UUID сервера из адресной строки панели |
| `tickets.cooldown-seconds` | пауза между `/ticket` одного игрока |

Нажмите **Save Content**, затем **Restart** сервера.

### Что должно получиться

В консоли сервера:

```
[AurumCompanion] HTTP-сервер companion слушает 0.0.0.0:8085 — порт не должен быть доступен из интернета
```

### Если не получилось

| Сообщение в консоли | Причина и что делать |
| --- | --- |
| `в config.yml не задан token` | поле `token` пустое или осталось `CHANGE_ME` |
| `token короче 16 символов` | слишком короткий; сгенерируйте заново |
| `token содержит не-ASCII символы` | кириллица в токене; сгенерируйте `openssl rand -base64 32` |
| `Не удалось занять порт 8085` | порт не выдан серверу как allocation (часть 2) или занят |
| `Команда /ticket отключена: не задан panel.server-id` | не заполнен `server-id` |
| `Панель не отвечает: …` | связь с панелью не установилась; разбор причин — в части 6 |

## Часть 5. Открыть порт в фаерволе

Если вы уже прошли шаг 1 инструкции по деплою и добавили порт `8085` в список
`RULES` — этот пункт пропустите.

Иначе **на домашнем сервере**:

```bash
sudo ufw allow from 10.0.0.1 to any port 8085 proto tcp comment 'companion-плагин'
sudo ufw status verbose
```

Проверка **с VDS**:

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://10.0.0.2:8085/players
```

Ожидаемо: `401` — плагин отвечает, но требует токен. Это правильный ответ,
значит связь есть.

Если получили `000` или таймаут — пакет не доходит: проверьте правило
фаервола и что сервер запущен.

## Часть 6. Прописать плагин в панели

1. Откройте `https://manage.aurumgg.ovh` → нужный сервер.
2. Настройки модуля (доступно роли **ГМ**).
3. Companion-плагин:
   - **Адрес**: `http://10.0.0.2:8085`
   - **Токен**: тот же, что в `config.yml`
4. Сохраните.

### Проверка, что всё заработало

- Вкладка **Игроки**: появились колонки «Здоровье», «Положение», аватары
  игроков вместо квадратиков с буквами. Подсказка про companion-плагин исчезла.
- Вкладка **Инвентарь**: вместо инструкции — поле «Ник игрока». Введите ник
  игрока, который **сейчас в сети**, нажмите «Показать» — увидите сетку
  предметов.
- В игре напишите `/ticket проверка связи` → в чат придёт «Тикет создан»,
  а в панели, в разделе **Тикеты**, появится обращение.
- Ответьте на тикет из панели → игроку в чат придёт сообщение с пометкой
  `[Панель]`.

### Если не получилось

| Симптом | Причина |
| --- | --- |
| Вкладка «Инвентарь» всё ещё показывает инструкцию | адрес или токен не сохранены в панели; проверьте настройки модуля |
| «Companion-плагин не ответил» | сервер выключен, плагин не загрузился или порт закрыт фаерволом |
| «Игрок не в сети» | инвентарь доступен только для тех, кто сейчас играет |
| `/ticket` → «Не получилось отправить» | плагин не достучался до панели — **причина написана в консоли сервера**, см. таблицу ниже |
| `/ticket` → «Тикеты не настроены на этом сервере» | не заполнен `server-id` или `base-url` в `config.yml` |
| Ответ модератора не приходит игроку | доставка идёт через RCON `tell`; проверьте, что RCON настроен и игрок в сети |

#### `/ticket` не отправляется: как понять, почему

Игроку плагин всегда отвечает одинаково — «Не получилось отправить, попробуй
позже». Подробности он **намеренно** не показывает: адреса и порты внутренней
сети игроку знать незачем. Настоящая причина уходит в консоль сервера.

Плагин проверяет связь с панелью **на старте** и пишет вердикт сразу, не
дожидаясь первого игрока:

```
[AurumCompanion] Связь с панелью есть — /ticket будет работать
```

Если связи нет — строка `Панель не отвечает: …`, и дальше по ней:

| В консоли | Что случилось | Что делать |
| --- | --- | --- |
| `не удалось подключиться к 10.0.0.1:3001` | до порта не достучаться | На VDS: `ss -tulpn \| grep 3001`. Должно быть `10.0.0.1:3001`. Если там `127.0.0.1:3001` — панель в браузере работает (nginx ходит через loopback), а плагин снаружи достучаться не может. Поправьте `API_BIND=10.0.0.1` в `api.env` и `systemctl restart aurum-api` |
| `не удалось определить адрес …` | имя хоста не резолвится | опечатка в `panel.base-url`; во внутренней сети имён обычно нет — пишите IP |
| `панель не ответила вовремя` | пакеты уходят в никуда | туннель поднят? `wg show` на обеих машинах. Если на VDS включён фаервол — нужно правило на `wg0`, порт 3001 |
| `не удалось установить TLS-соединение` | в адресе `https://` | по внутреннему адресу панель слушает **http**, без сертификата. `base-url: "http://10.0.0.1:3001"` |
| `panel.base-url … не похож на адрес` | строка не разбирается как URL | забыта схема (`10.0.0.1:3001` вместо `http://10.0.0.1:3001`), лишний пробел или кириллица |
| `в panel.base-url стоит порт … — это порт самого плагина` | перепутаны два порта | см. врезку ниже |
| `панель отвергла токен сервера` | связь есть, не совпал токен | `token` в `config.yml` и токен в настройках модуля на странице сервера должны совпадать посимвольно |
| `панель ответила 403` | запрос пришёл не из приватной сети | плагин ходит на публичный домен вместо адреса туннеля — internal-эндпоинт такое не принимает |
| `панель разорвала соединение, не ответив` | соединение состоялось, ответа нет | сеть исправна, проверять её бесполезно; см. врезку ниже |

#### Почему curl доходит, а плагин — нет

Эта поломка отдельная, и коварна она тем, что **все проверки связи её
оправдывают**: `curl` с хоста отвечает 200, `wget` из контейнера отвечает 200,
туннель цел, порт слушается — а тикеты не уходят.

Причина в том, что клиент и `curl` шлют разные запросы. HTTP-клиент из JDK по
умолчанию просит HTTP/2, и по обычному `http://` это делается апгрейдом: к
запросу добавляются заголовки `Connection: Upgrade` и `Upgrade: h2c`.

Панель — Node, и к её HTTP-серверу прицеплен socket.io (через него работает
консоль сервера). Как только у Node-сервера появляется обработчик события
`upgrade`, **все** запросы с этим заголовком уходят в него мимо обычного
конвейера. socket.io видит чужой путь и молча закрывает сокет — ответа нет
вообще, и клиент получает голый `IOException`.

`curl` и `wget` такого заголовка не шлют, поэтому проходят обычным путём и
отвечают 200. Отсюда и картина «сеть работает, а плагин нет».

Плагин с версии, где это найдено, просит HTTP/1.1 явно. Терять нечего: панель
отвечает только по HTTP/1.1, HTTP/2 у неё нет ни в каком виде.

> Если будете писать к панели свой клиент — учтите то же самое. Любой клиент,
> который по умолчанию пробует HTTP/2 по plaintext, наткнётся на это же.

#### Два порта, которые путают

В `config.yml` их два, и они **не связаны между собой**:

| Поле | Что это | Откуда брать |
| --- | --- | --- |
| `http.port` | порт, который слушает **сам плагин** на игровом сервере | secondary allocation в Pterodactyl |
| порт в `panel.base-url` | порт **панели** на другой машине | `API_PORT` панели, по умолчанию `3001` |

Самая частая ошибка — вписать в `panel.base-url` порт из allocation игрового
сервера. Он там выглядит уместно: его только что выдали, он «наш», он рядом в
том же файле. Но панель на нём не слушает, и плагин стучится в собственный
номер порта на чужом хосте — соединения нет.

Коварство в том, что сообщение об этом («не удалось подключиться») отправляет
чинить сеть, в которой всё цело: и туннель, и фаервол, и контейнер работают
правильно. Поэтому плагин проверяет это отдельно и говорит прямо:

```
[AurumCompanion] Проверьте config.yml: в panel.base-url стоит порт 8083 —
это порт самого плагина (http.port), а нужен порт панели (обычно 3001).
```

#### Проверять надо оттуда, откуда ходит плагин

Это главная ловушка в диагностике, и в неё попадают все по очереди.

**С самого VDS** адрес `10.0.0.1:3001` отзовётся почти всегда: трафик к
собственному адресу идёт через loopback и не проходит ни через туннель, ни
через фаервол. Проверка оттуда не значит ничего.

**С хоста домашнего сервера** — уже лучше, это проверяет туннель:

```bash
curl -sv http://10.0.0.1:3001/api/health
```

Но и её мало. Игровой сервер работает **в контейнере Wings**, у которого своя
сеть: наружу он ходит через докеровский мост, а не напрямую с хоста. Ответ
`200 OK` с хоста и молчание из контейнера — совершенно обычное сочетание.

Проверка из той же сети, в которой живёт игровой сервер:

```bash
sudo docker run --rm --network pterodactyl_nw busybox \
  wget -qO- --timeout=5 http://10.0.0.1:3001/api/health
```

`pterodactyl_nw` — сеть Wings по умолчанию; если у вас другая, имя видно в
`sudo docker ps --format '{{.Names}}  {{.Networks}}'`.

- **Отвечает `{"status":"ok"…}`** — сеть ни при чём, смотрите `panel.base-url`
  и токен.
- **Молчит или таймаут** — из контейнеров нет маршрута до `10.0.0.1`. Смотрите
  в эту сторону: `net.ipv4.ip_forward`, политику цепочки `FORWARD` и правила
  `DOCKER-USER` — в них часто закрывают доступ контейнеров к локальным сетям,
  и вместе с ним закрывается туннель до панели.

Ту же проверку делает и сам плагин при старте — уже изнутри контейнера, и
поэтому его вердикт точнее любой команды с хоста.

## Как это устроено внутри

Полезно понимать, если что-то поведёт себя странно.

- **Основной поток сервера.** Bukkit API нельзя вызывать из посторонних
  потоков, а HTTP-запросы приходят именно оттуда. Плагин переносит каждое
  обращение к игре в основной поток и ждёт не дольше 3 секунд — зависший
  сервер не подвесит панель.
- **Команда `/ticket`.** Сетевой запрос уходит асинхронно: держать основной
  поток на время HTTP-вызова нельзя, иначе лагает весь сервер.
- **Кулдаун.** Пауза между обращениями одного игрока, чтобы тикеты нельзя
  было заспамить.
- **Секреты.** Токен не пишется в логи; в сообщениях об ошибках нет ни
  токена, ни адреса панели.
- **Инвентарь только для онлайн-игроков.** Панель преобразует ник в UUID по
  текущему списку тех, кто в сети.
- **Автодополнение в консоли.** Без плагина панель дополняет по своему списку
  команд (ваниль + команды из каталога быстрых действий) и подставляет ники
  тех, кто в сети. С плагином по Tab спрашивается сам сервер — тогда видны и
  команды сторонних плагинов, и их аргументы. Через RCON автодополнения не
  бывает вовсе: в протоколе есть только «выполнить команду» и «ответ».

## Контракт HTTP (для разработчиков)

Пропустите, если просто ставите плагин.

Авторизация везде: `Authorization: Bearer <token>`. Ответы — JSON в UTF-8.

### Панель → плагин

**`GET /players`**

```json
{
  "players": [
    {
      "uuid": "8667ba71-b85a-4004-af54-457a9734eed7",
      "name": "Steve",
      "health": 18.5,
      "maxHealth": 20,
      "world": "world",
      "x": 100.26, "y": 64, "z": -200.5,
      "ping": 42
    }
  ]
}
```

**`GET /players/known?query=&offset=&limit=`** — все, кто когда-либо заходил

Источник — ванильный список `Bukkit.getOfflinePlayers()`, поэтому сама запись
есть всегда. `limit` не больше 200 (по умолчанию 50), `query` — подстрока ника.
Снимок списка кэшируется на 30 секунд.

```json
{
  "players": [
    {
      "uuid": "8667ba71-b85a-4004-af54-457a9734eed7",
      "name": "Steve",
      "alias": "Стив",
      "op": true,
      "online": true,
      "registered": true,
      "lastSeen": 1700000000000
    }
  ],
  "total": 1,
  "authAvailable": true
}
```

Три поля зависят от соседних плагинов, и `null` в них значит «неизвестно», а не
«нет»:

- `alias` — ник из **EssentialsX**. Нет плагина или ник не задан → `null`;
- `registered` — есть ли аккаунт в **AurumAuth**. Нет плагина → `null` у всех,
  а `authAvailable: false` говорит панели не делить список;
- `lastSeen` — `0`, если сервер не помнит даты входа.

`op` — ванильные данные (`isOp()`), плагинов не требует.

Ник и признак регистрации добираются **только для видимой страницы**: ник
EssentialsX читается из файла игрока, то есть отдельным обращением к диску на
каждого. В списке сначала идут те, кто в сети, затем — по убыванию `lastSeen`.

**`GET /players/{uuid}/ips`** — известные адреса игрока

Историю ведёт **AurumAuth**. Без него список пуст — это не ошибка: ванильный
сервер адреса не хранит.

```json
{
  "addresses": [
    { "ip": "203.0.113.7", "firstSeen": 1600000000000, "lastSeen": 1700000000000 }
  ]
}
```

**`GET /players/{uuid}/inventory`**

```json
{
  "items": [
    {
      "slot": 0,
      "id": "minecraft:diamond_sword",
      "count": 1,
      "displayName": "Гроза",
      "enchantments": { "minecraft:sharpness": 5 },
      "lore": ["Легендарный клинок"]
    }
  ],
  "armor": [ { "slot": 3, "id": "minecraft:diamond_helmet", "count": 1, "displayName": null, "enchantments": {}, "lore": [] } ],
  "offhand": { "slot": 0, "id": "minecraft:shield", "count": 1, "displayName": null, "enchantments": {}, "lore": [] }
}
```

Нумерация как в Minecraft: `0–8` хотбар, `9–35` основной инвентарь, броня —
4 слота, `offhand` — предмет или `null`. Пустые слоты не передаются.
Игрок не в сети → `404`.

**`POST /players/{uuid}/inventory/{slot}`**

Тело `{"id":"minecraft:stone","count":3}` кладёт предмет в слот `0–35`;
пустое тело или `{"id":null}` очищает слот. Неизвестный материал → `404`.

**`POST /players/{uuid}/inventory/give`**

Тело `{"items":[{"id":"minecraft:stone","count":64},{"id":"minecraft:apple"}]}` —
выдать набор предметов, каждый в первый подходящий свободный слот. `count`
по умолчанию `1`, не больше `2304` (полный инвентарь одним материалом), строк
за раз — не больше `45`. Стаки крупнее максимального размера плагин режет сам.

```json
{
  "results": [
    { "id": "minecraft:stone", "requested": 64, "given": 64, "error": null },
    { "id": "made_up", "requested": 1, "given": 0, "error": "Неизвестный предмет" }
  ]
}
```

Ответ построчный и всегда `200`, даже когда не легло ничего: запрос исполнен,
а вот инвентарь оказался полон или в строке опечатка — и панель должна
показать, какая именно строка не прошла. Игрок не в сети → `404` с
`{"code":"player-offline"}`.

**`POST /players/{uuid}/inventory/clear`**

Тело `{"slots":[0,9],"armor":[3],"offhand":true}` — очистить выбранное;
`{"all":true}` — весь инвентарь целиком вместе с бронёй и второй рукой.
Индексы брони `0–3` в порядке Bukkit: ботинки, поножи, нагрудник, шлем — то
есть ровно те же, что в массиве `armor` ответа выше.

Пустой выбор (`{}`, `{"slots":[]}`) — `400`, а **не** полная очистка. Разница
здесь необратимая, и потерянное по дороге поле не должно оборачиваться
стёртым инвентарём.

**`GET /plugins`**

```json
{ "plugins": [ { "name": "Essentials", "version": "2.20.1", "enabled": true } ] }
```

Имя — то, под которым плагин зарегистрирован в Bukkit. По нему панель решает,
показывать ли действия, которые без этого плагина не работают.

**`GET /players/{uuid}/permissions`** и **`POST /players/{uuid}/permissions`**

Группы и права игрока через LuckPerms. Без LuckPerms — `404` с
`{"code":"requires-luckperms"}`; отказ по состоянию (нет такой группы) —
`409` с `{"code":"rejected"}` и причиной.

**`GET /players/{uuid}/balance`**

```json
{ "balance": 1234.5, "formatted": "1 234,50 монет", "currency": "монет" }
```

При активном AurumCore баланс читается из ledger; иначе используется Vault.
Оба варианта работают и для игроков, которых сейчас нет в сети.

**`POST /players/{uuid}/balance/deposit`** и **`POST /players/{uuid}/balance/withdraw`**

Сумма строго положительная, знак задаёт сам маршрут. Тело внутреннего запроса
панели к Companion выглядит так:

```json
{
  "amount": 100,
  "idempotencyKey": "a18456b1-b830-4fc4-adb4-f63c9c870eba",
  "actor": "panel-user-id",
  "reason": "компенсация за потерянный предмет"
}
```

`reason` обязателен. `actor` подставляет API панели из текущей сессии, а не
браузер пользователя. UUID генерируется один раз и повторяется после таймаута
с теми же направлением, суммой и причиной.

```json
{
  "ok": true,
  "code": "ok",
  "error": null,
  "balanceBefore": 1234.5,
  "balanceAfter": 1334.5,
  "formatted": "1 334,50 монет",
  "idempotencyKey": "a18456b1-b830-4fc4-adb4-f63c9c870eba",
  "source": "aurum",
  "duplicate": false
}
```

Отказ плагина экономики («не хватает средств») — это `200` с `ok:false` и его
текстом в `error`: запрос корректен, а причина отказа нужна панели целиком,
вместе с балансом до и после, чтобы записать её в журнал аудита.

При активном Core запись идёт нативно в ledger. Неопределённый ответ — `503`
с кодом `economy-unavailable`: проводка могла сохраниться, поэтому повторять
надо **тот же** ключ. Тот же ключ с другой суммой, направлением, автором или
причиной — окончательный `409 idempotency-conflict`. Абсолютный `set` через
HTTP пока намеренно не открыт: безопасная установка баланса требует отдельной
семантики, иначе промежуточная операция между попытками превратит retry в
неверное начисление или списание.

**`GET /economy/audit/{section}?currency=aurum&account=guild%3A42&limit=50`**

Нативный аудит активного AurumCore. `section` принимает только `overview`,
`ledger`, `policies`, `exchanges`, `holds` или `claims`; каждый запрос читает
ровно один раздел и возвращает не больше 200 строк. `account` применяется
только к `ledger` и использует стабильный ключ счёта: `player:<uuid>`,
`guild:<id>`, `treasury:global`, `arena_escrow:<id>` и т. п. Пустое значение
показывает последние операции всех счетов; неверный ключ не расширяет запрос,
а отклоняется.

Маршрут не имеет Vault fallback: Vault не хранит проводки, holds, версии
правил и карантин выдач. При недоступном Core ответ — `503` с кодом
`economy-audit-unavailable`. Панель загружает раздел только после открытия,
при переключении вкладки или ручном обновлении — фонового polling нет.

**Версионированные правила экономики**

- `GET /economy/rules/{policy|exchange}` возвращает только текущие канонические
  ревизии.
- `POST /economy/rules/{policy|exchange}/preview` принимает `id`,
  `expectedRevision` и полный объект строковых `fields`. Для новой записи
  ожидается ревизия `0`. Core повторно проверяет все поля и при успехе выдаёт
  привязанный к автору одноразовый токен на пять минут.
- `POST /economy/rules/apply` принимает этот `token`, того же `actor` и
  обязательную `reason`. Автор формируется API панели из аутентифицированной
  сессии; браузер подменить его не может.

Между preview и apply другая запись может изменить правило. Тогда atomic
revision guard отвечает `conflict`, показывает актуальную ревизию и ничего не
перезаписывает. Токен потребляется одной попыткой. `applied_reload_failed`
означает, что новая immutable-ревизия уже зафиксирована в MariaDB, но runtime
registry не удалось перечитать; такой запрос **нельзя повторять**, нужно
обновить список и устранить причину reload. Истёкший токен требует нового
preview. Эти маршруты доступны только с active AurumCore и не имеют Vault
fallback.

**`GET /economy?top=10`** — с активным AurumCore:

```json
{
  "source": "aurum",
  "total": 125340.5,
  "totalFormatted": "125 340,50 монет",
  "currency": "монет",
  "treasury": 9000,
  "treasuryFormatted": "9 000,00 монет",
  "moneySupply": 125340.5,
  "moneySupplyFormatted": "125 340,50 монет",
  "taxesCollected": 4212.75,
  "taxesFormatted": "4 212,75 монет",
  "top": [ { "name": "Alex", "uuid": "…", "balance": 42000, "formatted": "42 000,00 монет" } ]
}
```

Без него — по-старому, через Vault:

```json
{
  "source": "vault",
  "total": 125340.5,
  "totalFormatted": "125 340,50 монет",
  "currency": "монет",
  "playersCounted": 214,
  "top": [ { "name": "Alex", "uuid": "…", "balance": 42000, "formatted": "42 000,00 монет" } ]
}
```

`source` — то, по чему панель решает, что показывать. Разница между двумя
ответами не косметическая:

- **`total`** у Vault — сумма кошельков всех, кто когда-либо заходил; у ledger —
  денежная масса сервера. Это близкие, но разные величины.
- **`playersCounted`** есть только у Vault, потому что там сумма и получается
  обходом игроков. У ledger её нет вовсе — не ноль, а отсутствующее поле:
  ноль означал бы «на сервере нет ни одного игрока».
- **`treasury`, `moneySupply`, `taxesCollected`** есть только у ledger. У Vault
  нет ни счёта сервера, ни понятия налога, и панель не рисует на их месте нули.

Стоимость запроса тоже разная: у ledger это один индексированный запрос, у
Vault — поход к экономике на каждого офлайн-игрока. Результат в обоих случаях
кэширует **панель** (пять минут либо кнопка «обновить»), а плагин каждый раз
считает честно. `top` ограничен сотней строк.

**Начисления и списания при `ACTIVE` идут через `AurumEconomyApi`, а не через
Vault.** Это даёт ledger категорию, автора, причину и защиту повторов. После
таймаута отката на Vault нет: commit мог уже состояться. Если Core отсутствует
или работает в `SHADOW`, Companion использует Vault для совместимости; у этого
fallback нет exactly-once гарантии.

Чтение различает `requires-vault` (нет ни активного Core, ни Vault) и
`no-provider` (Vault есть, но провайдера нет). Нативная запись дополнительно
может вернуть `economy-unavailable` и `idempotency-conflict`. Веб-маршруты
записи требуют отдельного ADMIN-only права `minecraft.economy.admin`;
устаревшее `minecraft.economy.edit` оставлено только для совместимости ролей.

**`GET /jails`** — тюрьмы EssentialsX и кто в них сидит

```json
{
  "available": true,
  "jails": ["main", "mine", "arena"],
  "jailed": [
    { "uuid": "…", "name": "Steve", "jail": "main", "releaseAt": 1700000000000 }
  ]
}
```

`available: false` значит «EssentialsX не отвечает или его версия
несовместима» — это **не** то же самое, что «тюрем не создано»: во втором
случае флаг стоит, а `jails` пуст.

Маршрут только **читает**. Сажает и выпускает панель обычной командой
`togglejail` по RCON, и это осознанно: у EssentialsX посадка — это ещё и
телепорт, событие `JailStatusChangeEvent` для других плагинов, сообщение
игроку и оповещение персонала. Дёрнув внутренний метод, мы получили бы
игрока в тюрьме, о котором никто не узнал.

Два ограничения списка `jailed`, оба принципиальные:

- в нём **только те, кто сейчас в сети**. Узнать про остальных можно, лишь
  прочитав файл каждого игрока в `userdata`, а их бывают десятки тысяч.
  Недостающих панель добирает из собственных записей;
- `releaseAt` — момент **выхода** (`0` — до отмены). Момента посадки
  EssentialsX не хранит вовсе, поэтому «сидит столько-то» панель знает
  только про тех, кого посадила она сама.

**`GET /players/{ник}/jail`** — сидит ли ОДИН игрок, включая офлайн

```json
{ "known": true, "jailed": true, "jail": "main", "releaseAt": 1700000000000, "online": false }
```

Адресуется **ником**, а не UUID: сажает панель по нику (его же принимает
`togglejail`), а офлайн-игрока может не оказаться ни в одном списке, откуда
UUID берётся.

`known: false` значит «EssentialsX такого игрока не знает» — ник с опечаткой
либо человек, который ни разу не заходил. Это **не** «не сидит», и путать их
нельзя: на «не сидит» панель отправила бы команду посадки тому, кто уже сидит.

Маршрут дополняет `GET /jails` ровно там, где тот бессилен: список сидящих
собирается по игрокам в сети и иначе не может, а посадить и выпустить панель
должна уметь и того, кого сейчас нет. Стоит вызов одного чтения файла игрока,
поэтому зовётся по одному на действие, а не списком.

**`GET /complete?line=<строка>`**

```json
{ "suggestions": ["gamemode", "gamerule", "give"] }
```

Автодополнение силами самого сервера — то же, что игрок видит по Tab в игре.
`line` — строка **без ведущего слэша** (ведущие слэши срезаются, длина
ограничена 256 символами). Возвращаются варианты целиком для последнего,
незавершённого слова: одно слово — имена команд, дальше — аргументы этой
команды, включая аргументы сторонних плагинов.

Внутри вызывается `CommandMap#tabComplete` от имени консоли сервера, поэтому
подсказки совпадают с тем, что консоли реально доступно. Пустой список — не
ошибка, а ответ «предложить нечего».

**`GET /guilds`**, **`GET /guilds/{id}`**, **`GET /players/{uuid}/guild`**

```json
{
  "guilds": [
    {
      "id": 7,
      "name": "Драконы",
      "tag": "DRG",
      "leaderUuid": "8667ba71-b85a-4004-af54-457a9734eed7",
      "leaderName": "Steve",
      "memberCount": 12,
      "bankBalance": 1200,
      "createdAt": 1767225600000,
      "members": []
    }
  ]
}
```

Гильдии живут не в companion, а в отдельном плагине **AurumGuilds**: companion
берёт его Java API из ServicesManager и работает мостом. Своего HTTP-сервера у
AurumGuilds нет намеренно — это был бы второй порт наружу и второй секрет в
конфиге.

`members` заполняется только в карточке (`GET /guilds/{id}`): в списке состав
не нужен, а тянуть по сотне участников на каждый показ — лишняя работа.
`GET /guilds?query=дра` ищет по имени и тегу.

Если AurumGuilds не установлен, весь раздел отвечает **503** с кодом
`guilds-unavailable` — не 404: маршрут существует и заработает, как только
плагин поставят. А вот игрок без гильдии — это **200** с `{"membership":null}`:
не состоять в гильдии нормально.

**`POST /guilds/{id}/disband`**, **`POST /guilds/{id}/transfer`**,
**`POST /guilds/members/{ник}/remove`**

Тело: `{"actor":"ГМ"}`, у transfer ещё и `{"target":"Steve"}`. `actor` попадает
в лог игрового сервера — там его читает администратор, у которого панели под
рукой может и не быть.

Ответ (и на успех, и на отказ — тогда **409**):

```json
{
  "ok": true,
  "message": "guild.admin.leaderSet",
  "values": { "player": "Steve", "guild": "Драконы" },
  "keys": {}
}
```

**`message` — это КЛЮЧ, а не фраза, и это изменилось.** Раньше плагин отдавал
сюда собранное по-русски предложение, панель показывала его как есть — и
сотрудник, переключивший интерфейс на английский, всё равно видел русский
ответ. Язык читателя знает панель, а не игровой сервер.

Подстановок две карты, и это не избыточность. В `values` то, что переводить
нельзя: ник, имя гильдии, сумма. В `keys` — то, что само является ключом
словаря: вид бонуса, ранг. Панель переводит `keys` и только потом подставляет;
сложи их в одну карту — и на экране окажется «mc.bonus.blockDrops» вместо
названия.

Имена ключей у плагина и у панели **общие** (`mc.bonus.*`, `mc.rank.*`): одно
и то же имя означает одно и то же слово по обе стороны.

**Так же устроены и остальные причины отказа.** `error` в ответе о выдаче
предметов (`mc.give.err.*`), о переключении плагина (`mc.plug.err.*`) и об
изменении прав (`mc.perm.err.*`) — тоже ключи, а не фразы. Технические
подробности, которые в ключ не влезают (класс исключения, имя не найденного
плагина), companion пишет **в журнал игрового сервера**: их читает тот, кто
чинит плагин, и читает он консоль.

**`GET /guilds/{id}/bonuses`**

```json
{
  "bonuses": [
    {
      "type": "block_drops",
      "title": "mc.bonus.blockDrops",
      "magnitude": 1.5,
      "multiplier": true,
      "expiresAt": 1789000000000,
      "grantedBy": "ГМ",
      "grantedAt": 1788900000000
    }
  ]
}
```

`expiresAt: 0` — бонус постоянный, а не «истёк в 1970-м»: постоянных бонусов
больше, чем временных, и отдельного поля-флага для этого не нужно.
`multiplier` говорит, как читать `magnitude`: `true` — это множитель (×1.5),
`false` — уровень эффекта зелья (1, 2, 3).

`title` — **ключ словаря** (`mc.bonus.blockDrops`), а не готовое название: имя
вида переводится на стороне того, кто смотрит. Имена ключей у плагина гильдий
и у панели общие, поэтому новый вид добавляется строкой в файл языка, а не
второй таблицей соответствий.

**`POST /guilds/{id}/bonuses`**

Тело: `{"type":"block_drops","magnitude":1.5,"seconds":604800,"actor":"ГМ"}`.
`seconds: 0` или без поля — навсегда. Величина **подрезается плагином** до
потолка вида, поэтому ответ надо читать, а не считать выданным то, что
попросили. Неизвестный вид — это осмысленный отказ с текстом, а не 503:
плагин-то на месте.

**`DELETE /guilds/{id}/bonuses/{вид}`**

Тело: `{"actor":"ГМ"}`. Снять несуществующий бонус — не ошибка.

### Плагин → панель

**`POST /api/internal/minecraft/servers/{serverId}/tickets`**

```json
{ "playerUuid": "…", "playerName": "Steve", "text": "меня загрифили" }
```

Ответ `{ "ticketId": "…", "created": true }` — по полю `created` плагин
выбирает, что написать игроку: «Тикет создан» или «Сообщение добавлено к
твоему тикету».

Вызывается core-сервис `createOrAppendTicket`, поэтому действует общее
правило: **один открытый тикет на пару (сервер, игрок)**.

Эндпоинт принимает запросы только из приватной сети (10.x, 172.16–31.x,
192.168.x, loopback) и наружу через nginx не публикуется.

## Известные ограничения

- Инвентарь игрока **не в сети** доступен, только если стоит **InvSee++**:
  и на чтение, и на запись. Ник при этом обязателен параметром `?name=` —
  InvSee++ адресует сохранённый инвентарь по нему, а не по UUID.
- У офлайн-инвентаря панель видит и правит основные 36 слотов. Броню, вторую
  руку и курсор офлайн-режим не показывает — и потому не трогает, в том числе
  при полной очистке.
- `POST` на изменение слота работает для основного инвентаря (0–35); броню
  и вторую руку у игрока **в сети** пока не меняет.
- Плагин рассчитан на Paper/Spigot. На ванильном сервере плагины не
  поддерживаются в принципе.
- Тюрьмы: `GET /jails` показывает сидящих **только из числа тех, кто в
  сети**, и не знает, когда человека посадили. См. раздел про этот маршрут
  и «Тюрьмы: чего от EssentialsX ждать нельзя» ниже.

## Тюрьмы: чего от EssentialsX ждать нельзя

Кнопки «В тюрьму» и «Выпустить» в быстрых действиях устроены не как остальные:
это не шаблон команды с подстановками, а последовательность, которую панель
собирает по текущему состоянию сервера. Причина — в самой команде
`togglejail`. Ниже то, что проверено по исходникам EssentialsX 2.x
(`Commandtogglejail.java`), а не выведено из документации.

**1. Перевести из одной тюрьмы в другую одной командой нельзя.** На
`togglejail игрок другая_тюрьма` по уже сидящему EssentialsX отвечает
`jailAlreadyIncarcerated` и **не делает ничего**. Панель поэтому переводит в
две команды: сначала выпуск, потом посадка заново. Цена — видимый скачок: на
выпуске игрока телепортирует из тюрьмы (куда именно, решает настройка
`teleport-when-free` самого EssentialsX), и следом он уезжает в новую.
Окно предупреждает об этом заранее.

**2. Срок в той же тюрьме заменяется, а не складывается.** Сообщение
называется «продлён» (`jailSentenceExtended`), но внутри это `setJailTimeout`
от «сейчас»: указали `30m` — сидеть остаётся ровно тридцать минут, сколько бы
ни оставалось до этого.

**3. «До отмены» через продление не выставить.** Ноль означал бы «выпустить
немедленно», а `togglejail игрок та_же_тюрьма` без третьего аргумента падает
на разборе пустой строки. Поэтому смена срока на бессрочный — тоже выпуск и
посадка заново.

**4. `togglejail` с одним аргументом по НЕ сидящему игроку сажает его**, если
на сервере настроена ровно одна тюрьма. Кнопка «выпустить» поэтому сначала
убеждается по списку от companion, что человек действительно сидит, и только
потом шлёт команду: кнопка выпуска, сажающая в тюрьму, — худшее, что тут
может случиться.

**5. Времени посадки в EssentialsX нет.** Он хранит только момент выхода
(`getJailTimeout()`, ноль — бессрочно). «Сидит столько-то» панель берёт из
своей таблицы `minecraft_jail_records` и показывает лишь тем, кого посадила
она сама; у посаженных в игре остаётся один остаток срока. Запись живёт,
пока человек сидит: выпустили через панель — удаляется, выпустили в игре —
снимается при первой же сверке со списком от плагина, когда игрок в сети.

**6. Офлайн-игрока посадить можно, и это работает как ожидается.**
`togglejail` принимает и того, кого нет на сервере: команда помечает игрока
сидящим, а телепорт откладывается — при входе `Jails` ловит `PlayerJoinEvent`
и отправляет человека в тюрьму сразу же, ещё и проверив, не вышел ли срок,
пока тот отсутствовал. Права `essentials.togglejail.offline` консоль RCON не
требует: проверка стоит только для отправителя-игрока.

Единственное, чего панель не умеет с офлайн-игроками, — **перечислить их**.
Список сидящих собирается по игрокам в сети; чтобы найти всех, пришлось бы
прочитать файл каждого, кто когда-либо заходил. Поэтому в окне выпуска
офлайн-сидельцы — это те, кого посадила сама панель: у неё есть своя запись, и
по ней она спрашивает сервер про каждого отдельно (`GET /players/{ник}/jail`).
Посаженного в игре офлайн-игрока в списке не будет — но выпустить его можно,
введя ник в поле посадки, и «Выпустить» рядом с ним сработает.

Про срок: по умолчанию он идёт и пока игрок офлайн. Если в `config.yml`
EssentialsX включён `jail-online-time`, отсчёт ведётся только по времени в
игре — тогда отсидка офлайн не засчитывается, и это настройка сервера, а не
панели.

## Обновление плагина

1. Соберите новый jar (часть 1.2).
2. Удалите старый из `plugins/` и загрузите новый.
3. Перезапустите сервер.

`config.yml` при обновлении не перезаписывается — настройки сохранятся.
