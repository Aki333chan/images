# AurumAuth — авторизация вместо AuthMe

Своя система входа для смешанного сервера: и лицензионные клиенты, и пиратские.
Хранилище — MariaDB, пароли — bcrypt, всё тяжёлое — вне главного потока.

## Почему отдельный плагин, а не часть companion

Авторизация по своей природе — хирургическое вмешательство в самый ранний этап
входа игрока: перехват join, движения, чата и команд на приоритетах, где ошибка
выглядит не как «не работает функция», а как «сервер никого не пускает».

Companion делает противоположное по характеру: держит HTTP-сервер, ходит в
Vault и LuckPerms, отправляет тикеты в панель. Если там что-то однажды
подвиснет — синхронный запрос, тяжёлая операция на главном потоке, — это не
должно иметь ни единого шанса задеть код входа.

Ровно поэтому и AuthMe — отдельный узкоспециализированный плагин, а не часть
чего-то большего.

## Из чего собран

| Модуль | Что внутри | Собирается |
| --- | --- | --- |
| `auth-api` | один интерфейс `AurumAuthApi` без зависимостей | любым JDK 21+ |
| `core` | конфиг, хранилище, bcrypt, сессии, троттлинг, premium | любым JDK 21+ |
| `paper` | слушатели, команды, регистрация сервиса | **только JDK 25** |

Логика живёт в `core` и покрыта тестами без запуска Minecraft. В `paper`
остаётся склейка.

## Схема

```sql
-- аккаунты
uuid              CHAR(36)     PRIMARY KEY
username          VARCHAR(16)  UNIQUE
password_hash     VARCHAR(120)
email             VARCHAR(190) NULL   -- задел под сброс письмом, пока не используется
registered_at     TIMESTAMP
last_login_at     TIMESTAMP    NULL
last_ip           VARCHAR(45)  NULL
totp_secret       VARCHAR(64)  NULL   -- двухфакторка, если игрок её включил
totp_enabled      TINYINT(1)
totp_last_counter BIGINT       NULL   -- защита от повторного ввода кода

-- <таблица>_resets   токены сброса пароля (только SHA-256 от токена)
-- <таблица>_logins   история входов, включая неудачные
```

Колонки двухфакторки добавляются к уже существующей таблице через
`ALTER TABLE … ADD COLUMN IF NOT EXISTS` при старте: `CREATE TABLE IF NOT
EXISTS` в таблице, заведённой прошлой версией плагина, их не создаст.

Одна база на все серверы сети даёт **сквозной вход**: зарегистрировался на
выживании — зашёл на креатив тем же паролем. Ключ — UUID, он везде одинаков.

Соединения берутся из пула (HikariCP). Новое соединение на каждый запрос — это
TCP-рукопожатие плюс аутентификация MariaDB на каждый вход игрока.

## Пароли — только вне главного потока

Это не оптимизация «на будущее», а условие работоспособности. bcrypt медленный
намеренно: при стоимости 12 одна проверка занимает около четверти секунды.
Синхронный вызов — это четверть секунды полностью остановленного сервера
(5 тиков). Несколько одновременных заходов, обычное дело после рестарта, дают
секунды лага **всем** игрокам, а не только тем, кто логинится.

Поэтому:

- `AuthService` — единственное место с обращениями к БД и bcrypt, и у него
  собственный пул потоков `AurumAuth-worker-*`;
- команды `/login` и `/register` получают `CompletableFuture` и возвращаются на
  главный поток через `runTask`, прежде чем что-то делать с игроком;
- `AsyncPlayerPreLoginEvent` — исключение: он и так вне главного потока, и
  перекладывать работу оттуда в ещё один поток незачем.

Это зафиксировано тестом: он проверяет, что после `login` и `register` в
хранилище не было ни одного обращения из вызывающего потока.

## Premium: где проходит граница честности

Сервер работает в offline-mode — иначе пиратские клиенты не подключатся.
Значит, криптографической проверки сессии на уровне протокола не существует
**в принципе**. Запрос к Mojang по нику отвечает ровно на один вопрос:
«существует ли лицензионная учётка с таким ником». Он не отвечает на вопрос
«тот ли это человек».

Поэтому вердиктов четыре, и пароль пропускает только один из них:

| Вердикт | Что значит | Пароль |
| --- | --- | --- |
| `PREMIUM_VERIFIED` | UUID подключения совпал с настоящим UUID из Mojang | **можно пропустить** |
| `PREMIUM_NAME_ONLY` | лицензия с таким ником есть, но UUID offline-овский | спрашивается |
| `OFFLINE_NAME` | лицензии с таким ником нет | спрашивается |
| `UNKNOWN` | Mojang не ответил, таймаут, проверка выключена | спрашивается |

Совпадение UUID подделать offline-клиентом нельзя: в offline-mode UUID
вычисляет сам сервер из ника (`UUID.nameUUIDFromBytes("OfflinePlayer:" + ник)`
— так это делает ванильный `LoginListener`), и с настоящим он не совпадает
никогда. Совпал — значит UUID подставило вышестоящее звено, то есть прокси,
проведшее для этого игрока настоящую online-mode авторизацию. Проверку сделали
не мы, но её достоверность настоящая.

**Следствие, о котором важно помнить:** на голом offline-сервере без прокси
`premium.skip-password` не сработает ни разу. Это не поломка, а правильный
способ ошибиться — пароль будет спрошен у всех. Плагин пишет об этом в лог при
старте.

Недоступность Mojang (429, 5xx, таймаут) трактуется как `UNKNOWN`, а не как
«лицензии нет»: чужая авария не должна менять поведение входа. Неудачные
ответы не кэшируются — иначе минута сетевых проблем на час закрепила бы
«не premium» за всеми, кто заходил в это время.

## Сообщения о входе: отложить, а не заглушить

### Из-за чего ссорятся AuthMe и EssentialsX

AuthMe обрабатывает `PlayerJoinEvent` на `LOWEST` и сразу делает
`setJoinMessage(null)`. EssentialsX обрабатывает то же событие на `HIGHEST`,
то есть **после**, и (проверено по исходникам `EssentialsPlayerListener`,
метод `joinFlow`) первым же делом проверяет:

```java
else if (message == null || hideJoinQuitMessages()) effectiveMessage = null;
```

`null` на входе для него означает «сообщения быть не должно», и ветка с
настроенным `custom-join-message` не выполняется вовсе. Погашенное на `LOWEST`
сообщение EssentialsX не восстанавливает и не перегенерирует — оно теряется
навсегда. Это и выглядит как «AuthMe съел мои join-сообщения».

### Что делает AurumAuth

Не мешает EssentialsX работать. Тот на `HIGHEST` формирует свой текст как
обычно, а мы вступаем на `MONITOR` — когда итоговое сообщение уже готово.
Забираем его, гасим показ, и после успешного входа рассылаем сами. Игрок видит
именно тот текст, который настроен в EssentialsX, просто на несколько секунд
позже.

Сообщение о **выходе** у не вошедшего гасится и не откладывается: о его
появлении никто не объявлял, и «игрок вышел» без предшествующего «игрок зашёл»
выглядит как сбой.

### Честно про цену

`MONITOR` по документации Bukkit предназначен только для наблюдения. Здесь он
изменяет событие сознательно: промежуточного приоритета между `HIGHEST` и
`MONITOR` не существует, а любое вмешательство **до** EssentialsX уничтожает
его сообщение — то есть выбор стоит между «нарушить соглашение о MONITOR» и
«повторить ровно ту поломку, от которой уходим».

Побочный эффект: плагины, которые тоже читают сообщение на `MONITOR` и
зарегистрировались после нас (мосты в Discord, например), увидят `null`.
Если это мешает — `join-messages.mode: ignore` выключает вмешательство целиком.

Механизм сверен по актуальным исходникам EssentialsX, но проверить его на живом
сервере с вашей сборкой всё равно стоит: у EssentialsX это внутренняя логика, а
не публичный контракт, и она может измениться.

## Просьба войти: почему не строчкой в чате

**Проблема.** EssentialsX показывает свой MOTD сразу после входа игрока — и
показывает его **не событием, а прямой отправкой текста**: в его исходниках это
`motdFlow` → `TextPager.showPage(..., user.getSource())`. Событие «игроку
пришёл текст» в Bukkit не существует, а значит перехватить, отложить или
погасить чужой MOTD нечем в принципе. MOTD в несколько строк уносит нашу
единственную подсказку вверх раньше, чем её успевают прочитать, и человек
стоит на спавне, не понимая, что от него хотят.

**Решение.** Не бороться за место в чате, а показывать подсказку там, откуда её
нечем вытеснить. Каналов три, и работают они одновременно:

| канал | почему он |
| --- | --- |
| **title поперёк экрана** | главный. Чат его не двигает вообще никак, и не заметить надпись во весь экран нельзя |
| **строка над горячей панелью** | постоянно на виду и не мешает читать чат |
| **строка в чате** | для тех, у кого title отключён в настройках клиента. Повторяется реже остальных — иначе это стена текста |

Всё это повторяется, пока игрок не вошёл: одного показа мало, если человек в
этот момент отвернулся или тянул ресурспак. В строке над панелью идёт обратный
отсчёт до кика (`{seconds}`).

Ступеней четыре, и у каждой свой текст: `login`, `register`, `totp` (пароль
принят, остался код), `new-password` (токен сброса принят). Ступень меняется —
меняется и надпись на экране, причём в чат при этом ничего не дублируется:
ответ команды человек только что прочитал.

**Всё настраивается** — раздел `prompt` в `config.yml`, цвета привычными кодами
`&a`, `&e`. Пустая строка выключает конкретную часть, не трогая остальные.
`/auth reload` перечитывает эти тексты на живом сервере.

Заодно перестал быть белым и остальной текст плагина: `prompt.prefix` и
`prompt.text-color` задают префикс и цвет всех его сообщений.

**Чужой MOTD мы не трогаем.** Если он мешает и сам по себе — у EssentialsX для
этого есть своя настройка `motd-delay` (в миллисекундах; отрицательное значение
выключает MOTD совсем). Решать за администратора, что показывать на его
сервере, не наше дело; наше — чтобы подсказку было видно при любом чужом MOTD.

## Что заблокировано до входа

Движение (только смена блока — осмотреться можно), чат, команды кроме
`/login`, `/register`, `/reset`, `/2fa` и их алиасов, взаимодействие с миром,
открытие инвентарей.

Список короткий сознательно. Каждый лишний перехваченный обработчик — ещё одно
место, где авторизация может поссориться с чужим плагином, а ровно от этого мы
и уходим.

Чат блокируется в том числе потому, что люди регулярно набирают пароль в чат,
промахнувшись мимо команды. Пропущенное сообщение означало бы пароль в общем
чате и в логах сервера.


### Подсказки по командам

Клиент получает список команд сервера сразу при подключении и показывает его по
нажатию `/`. Невошедшему это только мешает: выполнить он всё равно ничего не
может, а нужные `/login` и `/register` теряются среди полусотни чужих строк.
Поэтому до входа в списке остаются только команды входа
(`login.hide-other-commands`, по умолчанию включено), а дополнение по Tab для
чужих команд не возвращает ничего — ников онлайна невошедший не получит.

Делается это двумя событиями: `PlayerCommandSendEvent` (список верхнего уровня,
уходит клиенту один раз при входе) и `AsyncTabCompleteEvent` (дополнение
аргументов уже во время набора). После успешного входа список отправляется
клиенту заново — `Player#updateCommands()`, — иначе вошедший остался бы с
урезанным меню до перезахода, и выглядело бы это как «плагин сломал команды».

Это **видимость, а не защита**: скрытую команду клиент по-прежнему может
отправить строкой, и отбивает её запрет, а не этот список. Об этом честно
предупреждает и javadoc самого `PlayerCommandSendEvent`.

## Сброс пароля

Восстановления по почте пока нет, поэтому забытый пароль сбрасывает
администратор — из панели или командой.

1. **Панель**: карточка игрока → «Сбросить пароль». Кнопка есть у роли с правом
   `minecraft.password.reset` (по умолчанию только у Админа).
   В игре то же самое делает `/auth reset <ник>`.
2. Выдаётся **одноразовый токен из 8 знаков**, живёт 20 минут
   (`login.reset-token-minutes`).
3. Игрок заходит на сервер и вводит `/reset <токен>`.
4. Сервер просит новый пароль: `/reset <пароль> <пароль ещё раз>`.

Одна команда на обе ступени намеренно: человек, которому сбросили пароль,
помнит ровно одно слово. Ступени различаются числом аргументов, и различие
однозначно — токен всегда один аргумент из восьми знаков ограниченного
алфавита, новый пароль всегда два.

Что важно в реализации:

- **в базе лежит только SHA-256 от токена.** Дамп базы не должен давать вход
  тем, кому за последние 20 минут выдали сброс. bcrypt здесь не годится: по
  токену нужно НАЙТИ запись, а не проверить известную, и с солью на каждую
  строку пришлось бы перебирать всю таблицу;
- **токен привязан к UUID**: выданный для Стива не сработает у того, кто зашёл
  под другим ником;
- **гашение атомарно** — `UPDATE … WHERE used_at IS NULL` может выполнить
  ровно один запрос. Иначе два одновременных ввода одного токена оба прошли бы
  проверку;
- **принятый токен НЕ пускает в игру.** Он лишь переводит игрока в состояние
  «ждём новый пароль»: токен — ключ к смене пароля, а не вход;
- **новый пароль принимается только из этого состояния.** Без проверки вторая
  ступень стала бы способом сменить пароль любому, кто зашёл под чужим ником;
- новый токен гасит предыдущий, а сам сброс снимает блокировку по неудачным
  попыткам — иначе игрок с токеном упёрся бы в лимит, набранный тем, кто как
  раз и подбирал его пароль.

Токен показывается один раз: сервер хранит только хеш и повторить не сможет.
Потерянный — не восстанавливается, выдаётся новый.

## Двухфакторка по коду из приложения

Включает её **сам игрок**, командой:

```
/2fa enable          показывает секрет и ссылку для приложения
/2fa confirm <код>   подтверждает — только теперь она работает
/2fa <код>           ввод кода при входе
/2fa disable <код>   выключить
```

Стандарт TOTP (RFC 6238), то есть подходит любое приложение: Google
Authenticator, Aegis, 1Password, что угодно.

**Настройки «включить всем» нет намеренно.** Принудительная двухфакторка на
игровом сервере означает, что часть игроков просто перестанет заходить, а
часть потеряет доступ вместе с телефоном. Кому нужно — включит сам.

Как это устроено и почему именно так:

- **своя реализация вместо библиотеки.** Алгоритм — HMAC-SHA1 от номера
  тридцатисекундного интервала плюс выборка шести цифр; всё нужное есть в JDK.
  Корректность проверяется эталонными векторами RFC 6238 — то есть это ровно
  тот случай, когда своя реализация проверяема насквозь. Тесты гоняют её на
  всех шести официальных отметках времени; совпадение с ними и означает, что
  коды сойдутся с любым приложением;
- **подтверждение обязательно.** Между «сгенерировали секрет» и «игрок ввёл
  первый код» двухфакторка не действует. Иначе можно было бы включить её с
  секретом, который никуда не записан, и запереть себя снаружи аккаунта;
- **тот же код второй раз не проходит.** Код живёт полминуты, и подсмотренный
  через плечо (или продиктованный «сотруднику поддержки») он всё это время
  годен снова. Принятый номер интервала запоминается;
- **код подтверждения расходуется наравне со входом** — им самим войти уже
  нельзя;
- **выключить можно только действующим кодом.** Иначе двухфакторку снял бы
  любой, кто на минуту сел за компьютер с уже вошедшим игроком;
- **допуск на расхождение часов** — один интервал в каждую сторону
  (`totp.window`). Телефоны расходятся всегда; без допуска часть игроков не
  войдёт вовсе.

Потерянный телефон — случай администратора: `/auth 2fa-off <ник>`. Это обход
второго фактора, пусть и законный, поэтому право отдельное
(`aurumauth.admin.2fa`), а сам факт пишется в лог сервера.

## Удаление регистрации

**Игрок сам:** `/unregister <пароль>`. Пароль обязателен — команда стирает
аккаунт, и подтверждение здесь единственное, что отличает решение владельца от
шутки того, кто сел за его компьютер. После удаления игрок кикается: следующий
заход всё равно начнётся с регистрации.

**Администратор:** `/auth unregister <ник> confirm`. Слово `confirm`
обязательно, и перед ним команда прямо предупреждает о том, о чём легко забыть:

> Ник после снятия регистрации **освобождается**, и занять его сможет уже кто
> угодно. Как наказание это работает не так, как ожидается — если нужно
> закрыть ник, банить придётся отдельно.

Вместе с аккаунтом удаляются его токены сброса: оставленный токен от
удалённого аккаунта — мусор, который однажды сработает не на том, кого ждали.
История входов, наоборот, **остаётся**: она про то, что происходило, и
удаление аккаунта этого не отменяет.

## История входов

```
/auth history <ник> [1h|24h|3d|7d|30d]
```

Записываются **и неудачные попытки тоже**, и это главное. История нужна для
разговора «меня взломали»: успешные входы показывают, откуда заходили, а серия
отказов перед ними — что пароль перед этим подбирали. Одни успехи такой
картины не дают.

Различаются: вход по паролю, неверный пароль, неверный код двухфакторки, вход
по сессии, вход без пароля (premium или байпас), смена пароля по токену. «Вошёл
по паролю» и «пустили по сессии» — разные события, и при разборе инцидента
разница принципиальна.

Адрес показывается под тем же отдельным правом `aurumauth.admin.info.ip`, что и
в `/auth info`. Рядом с каждой строкой — имя сервера (`server-id` в конфиге):
база одна на всю сеть, и без него непонятно, где именно человек заходил.

Записи старше `history.keep-days` (по умолчанию 90) выбрасываются: бесконечная
история — это таблица, которая растёт весь срок жизни сервера.

## Команды администратора

```
/auth reset  <ник>            выдать токен сброса           aurumauth.admin.reset
/auth info   <ник>            что известно об аккаунте      aurumauth.admin.info
/auth unlock <ник>            снять блокировку по попыткам  aurumauth.admin.unlock
/auth logout <ник>            разавторизовать, погасить сессию  aurumauth.admin.logout
/auth history <ник> [период]  история входов                aurumauth.admin.history
/auth unregister <ник> confirm  снять регистрацию           aurumauth.admin.unregister
/auth 2fa-off <ник>           выключить двухфакторку        aurumauth.admin.2fa
/auth reload                  перечитать тексты сообщений   aurumauth.admin.reload
/auth help                    этот же список прямо в игре
```

`/auth help` и `/2fa help` показывают **строку на подкоманду** с коротким
описанием: раньше это была одна строка с перечислением через вертикальную
черту, из которой разница между `unlock` и `logout` не следует никак — а
ошибиться тут дорого, одна снимает блокировку, другая выкидывает игрока обратно
на экран входа. Длинный список режется на страницы по восемь строк
(`/auth help 2`), потому что больше в чате не видно, не разворачивая его.

**Тот же вид у любой подсказки.** Команда, набранная без аргументов, отвечает
строкой справки с описанием справа, а не голым «Использование: /login
&lt;пароль&gt;».

**Автодополнение подсказывает ники только тем подкомандам, которые их
принимают.** Раньше правило было обратным — «ники везде, кроме `reload`», — и
на `/auth help` предлагалось выбрать игрока, которого эта команда не берёт
вовсе. Такое ломается само собой: стоит добавить подкоманду без ника, и её
забывают внести в список исключений.

Ники предлагаются **только из тех, кто в сети**, хотя половина этих команд
работает и с офлайн-игроками. `getOfflinePlayers()` на живом сервере
возвращает всех, кто когда-либо заходил, — тысячи имён на каждое нажатие Tab
в главном потоке. Ник офлайн-игрока администратор всё равно откуда-то берёт:
из жалобы или из панели.

`/2fa` тоже дополняется — но **только названиями шагов**, никогда самим кодом:
он одноразовый и живёт полминуты, но подставлять его в строку команды, которая
уходит в историю чата и в логи, плагин не должен.

Одна команда с подкомандами, а не восемь отдельных: `/info` и `/reload` заняты
примерно везде, и каждая команда верхнего уровня — это ещё один шанс
столкнуться именами с чужим плагином.

`aurumauth.admin` — зонтичное право, включает все подкоманды. Кроме одной:
**`aurumauth.admin.info.ip` даётся отдельно** — адрес последнего входа это
сведения о человеке, а не о сервере, и выдавать их заодно с остальным
администрированием не стоит.

`/auth logout` — для случая «аккаунт увели»: пароль сменят потом, а перестать
пускать нужно сейчас. Гасит и сессию, иначе переподключение вернуло бы доступ
без пароля.

**Команды «задать игроку пароль» нет намеренно.** Пароль в аргументе попадает
в историю команд, в лог консоли и в чужие плагины логирования. Сброс токеном
решает ту же задачу, не создавая долгоживущей копии пароля.

### Право обхода пароля

`aurumauth.bypass` пропускает игрока без пароля. Под двумя замками: само право
(по умолчанию ни у кого, не входит ни в какие `children`) и переключатель
`login.permission-bypass` (по умолчанию `false`).

**На offline-сервере это опасная настройка**, и вот почему: UUID там
вычисляется из ника, значит подключившийся под ником администратора получает и
его UUID, и его права в LuckPerms — включая само право обойти пароль. То есть
удобство для админа превращается в способ зайти админом. Осмысленна она в
основном за прокси, где вход уже подтверждён по-настоящему. Каждое
срабатывание пишется в лог.

## Свои сообщения и приветствие

Раздел `messages` в конфиге — на случай, когда EssentialsX (или другого
плагина для этого) на сервере нет:

- `messages.join` — своё сообщение о входе, с отдельным текстом для того, кто
  только что зарегистрировался;
- `messages.quit` — своё сообщение о выходе;
- `messages.motd` — приветствие лично вошедшему, списком строк.

Цвета — привычными кодами `&a`, `&e`, `&6`, как в конфигах EssentialsX.
MiniMessage (`<green>`) намеренно не разбирается: человек, переносящий текст из
старого конфига, не должен обнаружить в чате «&e» вместо жёлтого.
Плейсхолдеры: `{player}`, `{online}`, `{max}`.

**Всё выключено по умолчанию.** Если EssentialsX стоит, он уже показывает свои
сообщения, и включённые здесь дадут второе подряд. Когда свои тексты включены,
они ЗАМЕНЯЮТ чужое сообщение (гасится даже у вошедшего по сессии) — два
сообщения о входе подряд хуже, чем любое одно.

Неизвестный плейсхолдер остаётся в тексте как есть: так опечатку в конфиге
видно сразу, а не «пропало слово». Подстановка идёт одним проходом по шаблону —
иначе ник вида `{online}` на следующем шаге превратился бы в число.

## Совместим с EssentialsX, но не зависит от него

Проверяемые факты, а не обещание:

- в коде плагина **нет ни одного упоминания EssentialsX** — ни импорта, ни
  обращения к его API, ни проверки «установлен ли он»;
- в `plugin.yml` **нет ни `depend`, ни `softdepend`** на него. Разведение
  приоритетов целиком в аннотациях `@EventHandler` и от порядка загрузки не
  зависит;
- единственные внешние зависимости — bcrypt, HikariCP и драйвер MariaDB, все
  внутри jar.

Что это даёт на практике:

| | EssentialsX стоит | EssentialsX нет |
| --- | --- | --- |
| сообщение о входе | придерживается его текст, показывается после входа | придерживается ванильный, показывается после входа |
| свои тексты `messages` | выключены — иначе будет два сообщения | включаются и работают |
| приветствие при входе | его `/motd`, если настроен | `messages.motd` |
| просьба войти | title и строка над панелью — его MOTD их не вытесняет | то же самое |
| всё остальное (вход, сессии, сброс, лимиты) | работает одинаково | работает одинаково |

## Сессии и защита от подбора

**Сессия.** Переподключился в течение `session-minutes` (по умолчанию 15) с
того же адреса — пароль не спрашиваем. Привязка к IP обязательна: без неё
достаточно дождаться, пока игрок выйдет, и зайти под его ником. Сессии живут в
памяти и не переживают перезапуск сервера — после рестарта разумнее спросить
пароль заново.

**Подбор.** Минимальная пауза между попытками плюс блокировка аккаунта на
несколько минут после серии неудач. Это не антибот — от массового захода
защищает сетевой уровень, — а базовая гигиена по конкретному аккаунту. Счёт
ведётся по нику: перебирают именно аккаунт, а адрес сменить проще, чем угадать
пароль. Обратная сторона — чужими неудачными попытками можно временно закрыть
вход владельцу, поэтому блокировка короткая и снимается сама.

Текст отказа одинаков для «неверный пароль» и «такого аккаунта нет»: разница в
формулировке позволила бы собрать список зарегистрированных ников, не подобрав
ни одного пароля.

## Событие об удалении аккаунта

У других плагинов заводятся собственные данные, привязанные к игроку: гильдии,
дома, кошельки. После удаления регистрации они остаются висеть на UUID, за
которым больше никого нет, — а на offline-сервере этот же ник вместе с UUID
может занять уже другой человек.

Поэтому при удалении шлётся `PlayerAccountDeletedEvent` (пакет
`ovh.aurumgg.auth.event`, модуль `auth-events`): UUID, ник на момент удаления и
флаг `byAdmin` — своё удаление это уход, административное наказание.

Уведомление живёт в `AuthService`, а не в обработчиках команд, и это не мелочь:
если бы о событии сообщали команды, то третий путь удаления — из панели, чистка
неактивных — молча остался бы без события, и обнаружилось бы это по чужим
данным на несуществующем аккаунте.

Событие шлётся **в главном потоке**, хотя само удаление идёт в рабочем:
обработчику почти наверняка понадобится Bukkit API. Игрока при этом может не
быть в сети — `/auth unregister <ник>` работает и по офлайн-игроку.

Модуль `auth-events` отдельно от `auth-api` намеренно: событие наследуется от
`org.bukkit.event.Event` и тянет за собой paper-api, а `auth-api` обязан
оставаться совсем без зависимостей — против него собирается companion.

Подписчику достаточно `compileOnly`-зависимости: класс события лежит внутри
jar самого AurumAuth. Так это и сделано в AurumGuilds — там слушатель
регистрируется только после проверки, что плагин авторизации установлен.

## API для других плагинов

`AurumAuthApi` регистрируется в `ServicesManager` — тем же приёмом, что Vault:

```java
RegisteredServiceProvider<AurumAuthApi> registration =
        Bukkit.getServer().getServicesManager().getRegistration(AurumAuthApi.class);
boolean logged = registration.getProvider().isAuthenticated(playerUuid);
```

Всё, кроме `isRegistered`, отвечает по памяти и безопасно с главного потока.
`isRegistered` ходит в базу и потому возвращает `CompletableFuture`.

Именно этим companion теперь заменил чтение `isLogged`/`hasSession` из таблицы
AuthMe: ни SQL, ни чужих паролей в конфиге, а схема таблицы становится
внутренним делом этого плагина.

## Что не сделано намеренно

**Восстановление пароля письмом.** Колонка `email` заведена и допускает `null`,
но нигде не используется: адресов никто не собирает. Сброс сейчас идёт через
администратора (см. выше) — рассылка пойдёт через SMTP, когда дойдёт очередь,
и токен для неё уже есть тот же самый.

**Резервные коды двухфакторки.** Потерянный телефон сейчас лечится командой
администратора (`/auth 2fa-off`). Одноразовые резервные коды сделали бы игрока
самостоятельным, но это отдельная таблица и отдельный разговор про то, где он
их хранит.

**Принудительная двухфакторка для стаффа.** Технически это одна проверка при
входе, но решение не техническое: стафф с двухфакторкой, потерявший телефон,
теряет доступ к серверу в тот момент, когда он нужнее всего.

**Антибот.** Есть на сетевом уровне, дублировать не нужно.
