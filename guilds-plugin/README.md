# AurumGuilds — пати и гильдии

## Контекстная палка WorldGuard + FAWE

Если один и тот же материал назначен wand в WorldGuard и FAWE, AurumGuilds
разрешает конфликт сам. Внутри существующего региона клик показывает его id,
приоритет, владельцев и привязанную гильдию, не меняя выделение. На свободной
земле ЛКМ и ПКМ ставят позиции 1 и 2 через публичный WorldEdit API, который
реализует FAWE. Администратор с `aurumguilds.region-wand.bypass` может поставить
точку внутри региона через Shift-клик. Настройки находятся в `region-wand`.

Пати (временные группы) и гильдии (постоянные) с сайдбаром, приватными чатами,
общаком и меню настроек. Управляется и из игры, и из панели.

## AurumUI

С версии 0.2.0 плагин поддерживает необязательный Fabric-клиент AurumUI через
AurumCompanion. У игрока без мода остаётся обычный общий sidebar гильдии и
пати. После handshake гильдия и пати публикуются как два отдельных компактных
блока у правого края, а чужой scoreboard не перезаписывается.

Зависимость мягкая: без AurumCompanion или без клиентского мода механика,
команды, база и классический HUD продолжают работать как раньше.

## Почему отдельный плагин, а не часть companion

Та же причина, по которой отдельным плагином сделана авторизация. Companion —
это мост к панели: HTTP-сервер, тикеты, чтение чужих плагинов. У него уже
набралось больше ролей, чем стоило бы одному плагину. Гильдии же — это
самостоятельная игровая механика с собственными данными, полутора десятками
команд, кликабельным меню и постоянно работающей задачей отрисовки. Смешать их
значило бы получить плагин, который нельзя ни выключить по частям, ни
перезагрузить, не задев всё остальное.

**Второго HTTP-сервера при этом не появляется.** AurumGuilds выставляет свой
Java API через `ServicesManager`, а companion — у которого сервер, токен и
канал к панели уже есть и уже проверены — подключается к нему мостом. Ровно так
же устроены Vault, LuckPerms и наша система авторизации. Иначе на игровом
сервере был бы второй порт наружу, второй секрет в конфиге и второе место, где
это можно настроить неправильно.

## Из чего собран

| Модуль | Что внутри | Чем собирается |
| --- | --- | --- |
| `guilds-api` | интерфейс и типы для других плагинов | любой JDK 21+ |
| `core` | вся логика без Bukkit: конфиг, хранилище, гильдии, пати, содержимое сайдбара | любой JDK 21+ |
| `paper` | адаптер к Bukkit: команды, слушатели, сайдбар, меню, мосты | JDK 25 (Paper 26.x) |

Всё, что легко ломается молча — разбор конфига, правила гильдий, наследование
лидерства, содержимое сайдбара, — лежит в `core` и покрыто обычными
JUnit-тестами без запуска Minecraft.

## Ни одной жёсткой зависимости

Это главное архитектурное требование плагина, и держится оно на трёх вещах:

1. в `plugin.yml` **нет ни одного `depend`** — только `softdepend`, который
   влияет лишь на порядок загрузки;
2. классы каждого соседа собраны **в одном файле-мосте**, и объект моста
   создаётся только после проверки через `PluginManager`, то есть до первого
   касания его классов. Нет плагина — класс не загружается вовсе, и
   `NoClassDefFoundError` не возникает;
3. вместо моста подставляется заглушка (`GuildHooks.noop()`,
   `EconomyBridge.unavailable()`), а логика гильдий вообще не знает, кто за
   интерфейсом стоит.

| Чего нет на сервере | Что перестаёт работать | Что продолжает работать |
| --- | --- | --- |
| **LuckPerms** | тег не показывается суффиксом к нику | всё остальное: команды, состав, банк, HUD, чат |
| **AurumCore** | у гильдии нет собственного счёта: банк работает через Vault, числом в нашей таблице | всё остальное |
| **Vault** (и AurumCore тоже нет) | команды банка отвечают «недоступно», в HUD нет строки про общак | всё остальное |
| **AurumAuth** | удаление аккаунта не убирает игрока из гильдии автоматически | всё остальное; убрать вручную — `/guild admin remove` |

При старте плагин пишет в лог отдельной строкой по каждому из трёх: что найдено
и что именно выключено. Строчки «AurumGuilds включён» без подробностей быть не
должно — иначе администратор узнает об отсутствии суффиксов от игроков.

## Данные

Пати живут **только в памяти**. Их собирают на один поход и распускают через
полчаса; писать это в базу значило бы платить запросом за каждое приглашение
ради данных, которые в следующий раз никому не понадобятся. Перезапуск сервера
распускает пати, и это правильное поведение, а не потеря данных.

Гильдии — в MariaDB, пять таблиц:

```
<префикс>            id, name, tag, leader_uuid, bank_balance, настройки, created_at
<префикс>_members    uuid (PK), guild_id, username, rank_name, joined_at
<префикс>_bank_log   guild_id, actor_uuid, actor_name, deposit, amount, balance_after, at
<префикс>_bonuses    (guild_id, type) PK, magnitude, expires_at NULL, granted_by, granted_at
<префикс>_regions    (guild_id, world, region_id) PK
```

Таблицы бонусов и регионов создаются при старте сами, как и остальные, — руками
ничего накатывать не нужно. `expires_at NULL` означает постоянный бонус, а не
«неизвестно когда»: это единственное состояние, которое там бывает кроме даты.

Первичный ключ таблицы участников — `uuid`, а не пара `(guild_id, uuid)`: игрок
состоит максимум в одной гильдии, и **база должна гарантировать это сама**.
Иначе ошибка в коде дала бы человека сразу в двух гильдиях, и выяснилось бы это
по двум суффиксам у его ника. Уникальные ключи на `name` и `tag` — по той же
причине: проверка «занято ли имя» и вставка идут двумя запросами, между которыми
успевает вклиниться второй игрок.

Лог банка — **без внешнего ключа и без каскада**: он переживает и уход
участника, и роспуск гильдии. Вопрос «куда делись двадцать тысяч из общака»
возникает не в момент операции, а через неделю — и как раз тогда, когда гильдии
уже нет.

### Одна база на один сервер

В отличие от базы авторизации, эту **не стоит делить между серверами сети**.
Гильдии живут в памяти плагина (иначе HUD и чат упирались бы в базу на каждом
кадре), а механизма оповестить соседний сервер об изменении здесь нет: он
продолжил бы показывать состав, который уже поменялся. Сквозные гильдии на всю
сеть — это отдельная задача с шиной сообщений, и делать вид, что она решена,
было бы хуже, чем честно это написать.

## Лидерство

Правило одно и то же везде — при выходе лидера, при административном
исключении и при удалении аккаунта:

1. наследует **старший по рангу**;
2. среди равных — **вступивший раньше**;
3. гильдия распускается **только если не осталось никого**.

Однозначность здесь важнее гибкости: иначе при каждом удалении лидера
начинается спор о том, почему выбрали именно этого.

Отдельно: **выход лидера из игры (дисконнект) гильдию не трогает вообще**. Она
постоянная и ждёт его возвращения. А вот уйти командой, бросив гильдию, лидер не
может — сначала передать лидерство или распустить. Единственное исключение:
последний участник, он же лидер, выходит — тогда гильдия распускается сама,
потому что гильдия из нуля человек существовать не может.

## Тег и суффикс: как это работает без единой команды LuckPerms

Ни игроки, ни лидеры ничего не вводят и про LuckPerms знать не обязаны.

1. при создании гильдии заводится **своя группа** с техническим именем вида
   `guild_17`. Имя собирается из внутреннего id, а **не из тега**: тег меняется
   и содержит что угодно, вплоть до кириллицы, а имя группы должно быть и
   постоянным, и безопасным;
2. на группу вешается **одна** meta-нода `suffix` со значением тега;
3. участнику добавляется **наследование** от этой группы — суффикс приходит ему
   сам;
4. при смене тега правится **только нода на группе**. На гильдии в полсотни
   человек это одно обращение к LuckPerms вместо пятидесяти;
5. при роспуске группа удаляется целиком.

Тег обязателен уже при создании, а не «настроите потом»: это суффикс, который
видят все, и гильдия без него полдня существует безымянной строкой в списке.

## HUD: сайдбар, который не воюет за слот

Слот `SIDEBAR` на сервере один, и на этом же сервере стоит **GladiatorArena**.
По её исходникам (`updateScoreboards`) видно, что во время боя она **каждые два
тика** делает игроку `player.setScoreboard(...)` со своей доской ставок. Писать
в слот безусловно означало бы мигание с частотой десять раз в секунду.

**Событий у арены нет.** В её четырёх файлах нет ни одного `callEvent`, ни
одного собственного класса события и ни одного публичного метода, по которому
можно было бы узнать про вход в бой или выход из него — проверено поиском.
Подписаться не на что, поэтому проверяется сам слот:

- доска **наша** → обновляем строки;
- доска чужая, но слот **свободен** → занимаем;
- слот **чужой** → не трогаем ничего. Проверка идёт каждый цикл, поэтому как
  только слот освободится, сайдбар вернётся сам.

Приятное следствие: арена перед заменой запоминает текущую доску игрока и
возвращает её после боя. Если там стояла наша, она же и вернётся — две системы
расходятся мирно без единой строчки про арену с нашей стороны.

### Как рисуются строки

**Строка — это префикс команды, а не запись scoreboard.** Разница не
косметическая: запись (entry) — это ИМЯ участника таблицы, вроде ника игрока,
и форматирование в ней не разбирается вообще. Первая версия писала текст прямо
в запись, и на живом сервере коды цвета показывались буквами:
`&7Пати &8(&f1&8/&f4&8)`.

Поэтому запись — невидимый ключ (одиночный `§`-код, который ничего не рисует),
а текст лежит в `Team#prefix(Component)`. Так работают полноценные компоненты
Adventure, включая цвета и hex.

Побочно это сняло вторую проблему: раньше одинаковые строки приходилось
разводить хвостами `&r`, потому что записи уникальны по тексту и два
разделителя схлопывались в один. Ключи теперь фиксированы по номеру строки, и
совпадение видимого текста ничего не значит.

**Счёт справа скрыт** через `NumberFormat.blank()`. Сам счёт нужен — им задан
порядок строк, — но клиенту рисовать его незачем: это те самые красные цифры
у правого края.

**Положение сайдбара на экране изменить нельзя.** Он всегда у правого края и
по вертикали посередине; это рисует клиент, и ни API, ни пакеты на это не
влияют. Сдвинуть выше может только ресурспак или клиентский мод.

**Действующие бонусы — зелёными строками под блоком гильдии**, с коротким
остатком времени: `Блоки ×1.5  7д`. Без этого бонус на добычу неотличим от его
отсутствия: руда падает, а насколько её стало больше, на глаз не скажешь.
Постоянному бонусу таймер не показывается — отсчитывать нечего. Строк не больше
трёх: видов бонусов пять, и в редком случае, когда действуют все, остальные
сворачиваются в «и ещё N», иначе блок гильдии съел бы список пати, ради
которого сайдбар в бою и нужен. Полный список — в `/guild bonuses`, короткий —
ещё и в `/guild info`.

**Здоровье — процентами: `HP: 73%`**, с цветом от зелёного к красному.
Раньше это был один символ `●`, менявший цвет: он занимал меньше места, но по
нему нельзя было отличить «почти цел» от «вот-вот умрёт» — а именно это и нужно
знать про того, кому собираешься помочь. Ступеней цвета пять: плавного перехода
в палитре Minecraft всё равно нет. Живой игрок никогда не показывается как 0%
— иначе своих принимали бы за трупы. Оффлайн — `HP: ?`.

BossBar не используется: его занимает та же арена, и второй полосы там не
нужно.

## Что сделано ради tps

Плагин живёт в главном потоке сервера, и три его пути горячие по-настоящему.

**Сайдбар перерисовывается только когда изменился.** Задача HUD зовёт показ раз
в секунду на каждого игрока, а строки между двумя тактами обычно те же самые:
здоровье меняется не каждую секунду, состав пати тем более. Раньше каждый такт
разбирал пятнадцать строк из `&`-кодов в компоненты Adventure и слал столько же
пакетов обновления команд, плюс пакеты счёта и заголовка. Теперь показанное
запоминается, и трогается только то, что действительно поменялось; при
неизменных строках вся работа сводится к сравнению списка.

Счёт строк переставляется, только если список стал длиннее или короче: он
зависит от общего числа строк, поэтому при смене длины меняется у всех — а при
правке одного слова не меняется ни у кого.

**Бонусы ищутся циклом, а не потоком.** `multiplier()` зовут с каждого
сломанного блока, каждого убитого моба и каждой капли опыта. Поток с
лямбдой-фильтром создавал там три объекта на вызов ради перебора списка из
пяти элементов. У игрока без гильдии выход происходит на первой строке — за
этим проверка членства и стоит раньше всего остального.

**HUD не пересобирает то, что уже в руках.** Состав считается по самому
`StoredGuild`, а не через `memberUuids()`, который строил новый список на
каждого игрока каждую секунду. Ответ «работает ли банк» берётся один раз за
проход, а не на каждого: он одинаков для всех, а стоит обращения к реестру
служб Bukkit под общей блокировкой.

**Ник по имени не перебирает всех, кто когда-либо заходил.**
`Bukkit.getOfflinePlayers()` в `PlayerNames` заменён на
`getOfflinePlayerIfCached`: старый вариант просматривал весь usercache в
главном потоке на каждое `/guild kick` и `/party promote`.

## Перезагрузка настроек

```
/guild admin reload
```

Право `aurumguilds.admin`. Перечитывает `config.yml` без перезапуска сервера.

**Сервисы при этом не пересоздаются.** В них лежат собранные пати, кэш гильдий
и висящие приглашения — перезагрузка, которая всё это распускает, была бы
скрытым рестартом, а не перезагрузкой. Меняются только сами настройки:

| Применяется сразу | Требует перезапуска |
| --- | --- |
| лимиты пати и гильдий, длина имени и тега | адрес базы, префикс таблиц |
| срок жизни приглашений | размер пула соединений |
| заголовок и период обновления HUD, его включение | |
| префикс групп и формат суффикса LuckPerms | |
| включение банка | |
| урон своим в пати (`party.friendly-fire`) | |

Про базу и пул сказано отдельно и намеренно: пересоздавать подключение под
идущими операциями на живом сервере — способ потерять транзакцию с чужими
деньгами ради удобства, которое нужно раз в месяц. Если эти поля правили,
команда так и скажет.

Уменьшенный лимит пати **не разгоняет уже собранные группы**: человек ничего
не нарушал, он просто был в пати, когда админ правил число. Новых сверх лимита
позвать уже нельзя, и отказ приходит сразу на приглашение.

## Vault: почему провайдер спрашивается каждый раз

`softdepend: [Vault]` **недостаточно**, и на этом здесь уже обожглись.

Vault сам денег не хранит — это шина. Провайдера экономики регистрирует третий
плагин (EssentialsX, CMI, любой другой), в его собственном `onEnable`. В нашем
`softdepend` его нет и быть не может: мы не знаем, какой стоит на сервере. Значит,
он вполне может запуститься позже нас.

Первая версия спрашивала о провайдере ровно один раз, на старте, и, не увидев
его, навсегда подставляла заглушку. Банк оставался выключенным до перезапуска —
при живом и работающем Vault.

Поэтому вопрос задаётся при каждом обращении. Провайдер, появившийся через
минуту после старта, подхватывается сам; перезагруженный на ходу плагин
экономики не оставляет нас со ссылкой на мёртвый экземпляр. Проверка «есть ли
вообще Vault» стоит первой, чтобы на сервере без него задача HUD не упиралась
в `NoClassDefFoundError` несколько раз в секунду.

В логе состояние банка расписано тремя разными случаями — выключен в конфиге,
провайдера пока нет, работает, — потому что чинятся они по-разному.

## Меню настроек

`/guild settings` открывает обычный инвентарь. Клик гасится
(`event.setCancelled(true)`) **первой строкой обработчика, до любых проверок**:
иконки — настоящие предметы, и незакрытый клик означает, что игрок вынесет из
меню алмазный меч. Отдельно гасится перетаскивание — это другое событие.

Стартовый набор: дружественный огонь, тип вступления (открыта / по приглашению
/ закрыта), описание гильдии, кто распоряжается общаком, смена тега. Пункты
заданы списком, и **новая настройка — это один элемент в нём**: раскладка по
слотам и размер меню считаются сами.

Пункт про дружественный огонь прячется, если PvP выключено во всех мирах:
показывать настройку, которая ничего не меняет, значит обещать несуществующий
эффект. Пункт про банк прячется, когда банка нет.

## Банк гильдии

Своей валюты плагин не заводит — это была бы вторая экономика на сервере, где
уже есть одна.

Вкладывать может **любой участник** — это его собственные деньги, и запрещать
здесь нечего. Снимать — по настройке: только лидер (по умолчанию) или лидер и
офицеры. Каждая операция пишется в лог и оттуда не удаляется.

### Где лежат деньги: это не настройка, а следствие

| Что стоит на сервере | Где деньги банка | Чем это отличается |
| --- | --- | --- |
| **AurumCore** | на счёте `GUILD:<id>` в ledger | вклад и снятие — одна атомарная проводка; число `bank_balance` в нашей таблице становится зеркалом для HUD и панели |
| только **Vault** | числом в нашей таблице | как было: два независимых шага, общей транзакции между ними нет |
| ничего | — | команды банка отвечают «недоступно», остальное в гильдиях работает |

Классы AurumCore упоминаются ровно в одном файле (`AurumCoreBridge`), как и
классы Vault, LuckPerms и WorldGuard. Какой из двух мостов работает, решает
`GuildEconomy`: на старте — если AurumCore уже поднялся, иначе по событию
`ServiceRegisterEvent`, когда он поднимется.

**Переключение только в одну сторону.** Из Vault в ledger — да, обратно —
никогда. После переноса деньги *лежат* на счетах гильдий, и откат к Vault
означал бы, что банк снова работает по зеркалу, то есть выдаёт деньги, которых
на счёте уже нет. Выключили AurumCore — правильный ответ «банк недоступен», а
не «банк работает по старому числу».

### Перенос старых балансов

При первом запуске с AurumCore балансы банков переезжают на счета гильдий
проводкой из `SYSTEM_SOURCE:guild-bank-migration` категорией `MIGRATION`.

Это **перенос, а не начисление**. За числом в `bank_balance` стоит журнал
операций, и гильдия имеет право снять эти деньги прямо сейчас — проводка не
создаёт их, а даёт им владельца. Тем это и отличается от долгов AurumArena
1.4.0, которые сознательно **не** начисляются: за теми не стоит ни одной
проводки.

От повтора защищают две вещи, и обе нужны. Идемпотентный ключ
`guild-bank-migration:<id>` спасает от повторной проводки с той же суммой, но
после первого же вклада сумма станет другой — и второй перенос выглядел бы для
ledger новой законной операцией. Поэтому решает **отметка в таблице**
`<префикс>_bank_migrated`, а ключ остаётся страховкой на случай падения между
проводкой и отметкой. Порядок именно такой: обратный терял бы деньги.

Пока перенос по конкретной гильдии не прошёл, её банк отвечает «подождите»
(`guild.err.bankMigrating`), а не работает по старому числу.

> **Проверьте правила policy engine.** Они выбираются по категории операции, и
> общесерверное правило `TAX` вполне может задеть `GUILD_DEPOSIT` или
> `MIGRATION`. На переносе это особенно скверно: часть уже существовавших денег
> исчезнет при простой смене хранилища. Плагин такое замечает и пишет
> предупреждение в лог, но не отменяет.

### Порядок шагов при снятии

На ledger снятие — одна проводка «счёт гильдии → кошелёк игрока»: либо она
прошла целиком, либо не было ничего, и списывать с банка заранее не только не
нужно, но и вредно.

За Vault общей транзакции нет, и порядок — единственная защита. Сначала
списывается с банка и только потом выдаётся игроку: обратный порядок при отказе
выдачи оставил бы деньги и там, и там. Если выдача не прошла, сумма
возвращается **обратной записью**, а не правкой прежней — в логе должны
остаться оба движения, иначе разбор через неделю упрётся в снятие, которого на
самом деле не было.

### Роспуск с ненулевым общаком

Раньше вопроса не было: денег, которые могли бы куда-то деться, не
существовало — банк был числом, и строка просто удалялась. На счёте
`GUILD:<id>` лежат настоящие деньги, и оставить их там значит запереть сумму на
адресе, к которому больше нет ни одной команды: в денежной массе сервера она
есть, а достать её нельзя.

Судьба общака задаётся `bank.on-disband`:

| Значение | Что происходит |
| --- | --- |
| `leader` (по умолчанию) | всё лидеру: роспуск его решение, получатель один и заранее известен |
| `split` | поровну между участниками на момент роспуска, остаток от деления лидеру |
| `treasury` | в глобальную казну сервера; деньги меняют владельца, но остаются в общей денежной массе |
| `keep` | не трогать; останутся на счёте распущенной гильдии и будут доступны только через команды AurumCore |

**Это изменение поведения при обновлении с 0.3.0**, где общак просто исчезал.
На сервере без AurumCore у Vault нет счёта казны, поэтому только там `treasury`
повторяет старое поведение и удаляет число вместе с гильдией.

Доли считаются **в копейках целыми числами**: делить `double` на число
участников и раздавать частное — верный способ раздать на копейку больше или
меньше, чем было в банке, а расхождение в ledger на округление не спишешь.
Перед первой выплатой режим, исходный баланс и список участников записываются в
`<prefix>_disband_plans` и `<prefix>_disband_shares`. Пока план не завершён,
состав, настройки, бонусы и банк этой гильдии заморожены. Каждая выдача идёт со
стабильным ключом `guild-disband:<id>:<получатель>`, а отметка доли и строка
банковского аудита записываются одной транзакцией. После перезапуска минутный
housekeeping продолжает только неоплаченные строки; появление AurumCore запускает
продолжение сразу. В обычной работе обе таблицы пусты и не участвуют в HUD/чате.

С AurumCore потерянный ответ безопасен: повтор ключа возвращает ту же проводку и
не платит дважды. **У Vault идемпотентности нет**; сохранённый план уменьшает окно,
но авария ровно после выплаты Vault и до отметки строки всё ещё может её повторить.

Записи о выдачах попадают в тот же журнал банка, что и обычные снятия. Журнал
переживает роспуск (ни внешнего ключа, ни каскада) и отвечает на вопрос «куда
делся общак», который задают не в день роспуска, а через неделю.

## Бонусы гильдии

Усиления, которые действуют на **всех участников** гильдии — временно или
постоянно. Выдаются из панели (право `minecraft.guilds.manage`), командой
`/guild admin bonus grant` или из чужого плагина через Java API.

| Вид | Что делает | Играбельно | Потолок |
| --- | --- | --- | --- |
| `mining_speed` | эффект «Спешка» | уровень 1–3 | 30 |
| `movement_speed` | эффект «Скорость» | уровень 1–2 | 20 |
| `block_drops` | больше добычи из сломанных блоков | ×1.1–×3 | ×30 |
| `mob_drops` | больше добычи с убитых мобов | ×1.1–×3 | ×30 |
| `experience` | больше опыта — и с мобов, и отовсюду ещё | ×1.1–×3 | ×30 |

**Потолок — это предел техники, а не рекомендация.** Он отвечает на вопрос «что
сервер переживёт», а не «что стоит выдавать»: высокие значения оставлены для
тестового сервера, где работу бонуса надо увидеть сразу, а не через час добычи.
Что будет, если всё-таки выдать:

- ×30 превращает один сломанный блок в десятки предметов — это десятки сущностей
  на каждый удар киркой, и игрок с «Удачей» просадит tps сам;
- «Скорость» с пятого уровня воюет с проверкой сервера «moved too quickly»:
  игрока отбрасывает назад, и выглядит это как лаг, а не как усиление;
- «Спешка» выше пятого-шестого уровня уже ничего не меняет — блоки и так
  ломаются мгновенно.

Сам потолок при этом обязателен и проверяется при каждой выдаче — из игры, из
панели и через API: без него опечатка в одном нуле у NPC-торговца означала бы
×300.

**Ни одного боевого бонуса — намеренно.** Урон, броня и сопротивление
превратили бы гильдию из объединения в преимущество в бою, а на сервере с PvP
это меняет правила игры, а не облегчает её. Всё перечисленное ускоряет добычу и
передвижение, но не решает, кто кого убьёт.

**Один бонус каждого вида на гильдию.** Выдача поверх действующего заменяет
его, а не складывается: иначе десять раз выданный ×1.1 незаметно превращается в
×2.6, и никто не может сказать, откуда это взялось. В базе это первичный ключ
`(guild_id, type)`, а не соглашение в коде.

**Бонус СКЛАДЫВАЕТСЯ с зачарованиями, а не заменяет их.** Множитель считается от
того, что выпало бы и без бонуса, — то есть уже с «Удачей», «Добычей» и
шёлковым касанием. Кирка с «Удачей III» и гильдейский ×1.5 дают примерно
четыре-пять алмазов, а не полтора: чем лучше инструмент, тем больше даёт бонус.

Это обеспечено не формулой, а выбором точки: `BlockDropItemEvent` и
`EntityDeathEvent` несут добычу, которую сервер посчитал сам, и ссылки на
инструмент у этих событий нет вовсе — значит, зачарование применено раньше,
всегда. Арифметика вынесена в `core/BonusMath.java` и проверяется тестами,
включая проверку, что худший розыгрыш не опускает добычу ниже той, что дало
зачарование.

**Дробный множитель — это шанс, а не округление.** Множитель ×1.5 на одном
алмазе не может дать полтора алмаза. Целая часть выдаётся всегда, дробная
разыгрывается: при ×1.5 к каждой единице добавляется ещё одна с вероятностью
50%. На длинной дистанции это ровно обещанные полтора раза, на одном блоке —
честная монетка. Округление вниз означало бы, что ×1.5 не делает ничего для
всего, что падает поштучно; вверх — что ×1.1 работает как ×2.

**Добавка режется по размеру стопки.** 261 алмаз сверху — это пять стопок, а не
одна: `ItemStack` с количеством больше предела клиент рисует неправильно, а
часть предметов пропадает при первой же попытке положить их в сундук. Предел
берётся у самого предмета — у ведра он равен единице, у зелий трём.

**Предметы с зачарованиями не множатся.** Клонировать чужой именной меч — не
«повышенная добыча», а дублирование вещей.

**Эффекты продлеваются задачей, а не выдаются разово при входе.** Выданная один
раз «Спешка» погасла бы через минуту, и игрок решил бы, что купленный бонус не
работает; бесконечная длительность осталась бы висеть и после того, как бонус
сняли. Поэтому эффект короткий и обновляется каждые пять секунд: кончился бонус
— перестали продлевать, и он гаснет сам. Чужое зелье скорости II при этом не
понижается до гильдейской скорости I — так работает сама игра.

### Хук для NPC-торговцев

Чтобы бонусы можно было **продавать** в игре, `AurumGuildsApi` (тот же, что
выставлен через `ServicesManager`) отдаёт их наружу:

```java
var api = Bukkit.getServicesManager().load(AurumGuildsApi.class);
if (api != null) {                       // плагина может не быть
    api.grantBonus(guildId, BonusType.BLOCK_DROPS, 1.5, Duration.ofDays(7), "NPC-торговец");
    api.revokeBonus(guildId, BonusType.BLOCK_DROPS, "NPC-торговец");
    api.bonuses(guildId);                // что уже действует
    api.bonusOf(playerUuid, BonusType.EXPERIENCE);
}
```

Величина сама подрезается до потолка вида — торговцу не нужно знать границы,
чтобы не выдать ×100. Кто выдал, пишется строкой и видно в `/guild bonuses` и в
панели: через неделю вопрос «откуда у них это» задают именно так.

## Дома гильдий: WorldGuard

Лидер приватит территорию и командой `/guild claim <регион>` выдаёт доступ туда
**всей гильдии**. Дальше состав держится в согласии сам: вступил — добавили в
регион, вышел или выгнали — убрали. Вручную об этом не забывают ровно до первой
ссоры, после которой выгнанный по-прежнему заходит в гильдейские сундуки.

Трогается **только список участников региона** (`members`). Владельцы
(`owners`) не трогаются никогда: владелец — тот, кто регион создал, и отобрать
у него права плагин гильдий не вправе. Флаги, границы и приоритет региона тоже
не наши. Привязать можно только регион, **владельцем** которого игрок является,
— иначе любой участник чужого привата раздавал бы чужую землю.

Роспуск гильдии участников из региона **не убирает**, и это осознанно: регион
остаётся у своего владельца, а массово вычищать чужой приват на событии,
которое может оказаться ошибкой, — не то, что стоит делать автоматически.
Отвязать вручную: `/guild claim remove <регион>`.

WorldGuard в `softdepend`, классы `com.sk89q.*` упоминаются в одном
`WorldGuardBridge`, и объект создаётся только после проверки, что плагин есть.
Без WorldGuard команда честно отвечает, что привязывать не к чему.

## Команды

### Пати

| Команда | Что делает |
| --- | --- |
| `/party create` | создать |
| `/party invite <ник>` | позвать — может **любой участник**, а не только лидер |
| `/party accept [ник]` | принять; без ника — самое свежее приглашение |
| `/party leave` | выйти |
| `/party kick <ник>` | выгнать (только лидер) |
| `/party promote <ник>` | передать лидерство (только лидер) |
| `/party list` | состав |
| `/party help` | список команд с описанием |
| `/p <сообщение>` | чат пати |

**Урон своим в пати по умолчанию выключен.** Меняется в `config.yml`
(`party.friendly-fire`) или командой `/guild admin friendlyfire on|off` — она
пишет в конфиг, так что переживает перезапуск. Это настройка **всего сервера**,
в отличие от гильдейского PvP, который каждая гильдия включает себе сама в
`/guild settings`.

Приглашение истекает само (по умолчанию через 90 секунд). Вышедший из игры из
пати **не удаляется**: разрыв связи не должен разваливать группу, в сайдбаре он
показан серым. Брошенные пати убираются, когда в них никого нет в сети дольше
пятнадцати минут.

| Команда | Право |
| --- | --- |
| `/guild admin remove <ник>` | `aurumguilds.admin` |
| `/guild admin transfer <гильдия> <ник>` | `aurumguilds.admin` |
| `/guild admin disband <гильдия>` | `aurumguilds.admin` |
| `/guild admin bonus list <гильдия>` | `aurumguilds.admin` |
| `/guild admin bonus grant <вид> <величина> [30m\|2h\|7d] <гильдия>` | `aurumguilds.admin` |

| `/guild admin friendlyfire [on\|off]` | `aurumguilds.admin` |

Работают **независимо от того, есть ли на сервере система авторизации**, и
доступны из консоли. Те же три действия есть в панели, во вкладке «Гильдии».

Право `aurumguilds.create` по умолчанию у всех: гильдии — это возможность для
игроков, а не привилегия. Ограничить можно переключателем
`guild.require-create-permission`, и тогда право придётся выдать явно.

Настройка групп в LuckPerms — в [`deploy/LUCKPERMS.md`](../deploy/LUCKPERMS.md),
там же про группы `guild_<id>`, которые плагин заводит себе сам.

## Помощь по командам

`/guild help`, `/party help`, `/2fa help` и `/auth help` показывают **строку на
команду**: слева — как набирать вместе с аргументами, справа — что она делает.
Раньше это были две-три плотных строки с перечислением через запятую; прочитать
их можно, а понять, что делает `demote` и в каком порядке ему давать аргументы,
— уже нет.

Длинная справка режется на страницы по восемь команд — ровно столько строк
видно в чате, не разворачивая его. Номер страницы за границами прижимается к
ближайшей, а не считается ошибкой. Администраторские команды показываются
только тем, у кого есть `aurumguilds.admin`: страницы тогда считаются по тому,
что человек реально увидит, и в конце не остаётся пустой страницы из скрытых
команд.

Разбиение живёт в `core/HelpBook.java` — без единого класса Bukkit, чтобы
проверяться обычным тестом: промах на единицу в постраничном выводе прячет
ровно одну команду, и заметить это глазами в чате почти невозможно.

**Тот же вид у любой подсказки.** Команда, набранная без аргументов, отвечает
не «Использование: /guild kick &lt;ник&gt;», а строкой справки — с описанием
справа. Что делает `kick`, из голой сигнатуры не следует никак, а человек,
ошибившийся аргументом, как раз и хочет это узнать. Если подсказка выглядит
одинаково всюду, её достаточно научиться читать один раз.

`/guild admin bonus` без аргументов показывает три действия и **перечень видов
с границами величин** — следующий вопрос после «bonus» именно про это, и
отправлять за ним в README значит заставить выйти из игры.

## Автодополнение

Каждая позиция знает, что на ней уместно, и общей ветки «а иначе имена
гильдий» нет вовсе — место без подсказки честно возвращает пустоту. Раньше
такая ветка стояла последней и ловила всё, до неё не дошедшее: на
`/guild admin bonus` Tab предлагал **имена гильдий** там, где нужно
`grant|revoke|list`.

| Где | Что предлагается |
| --- | --- |
| `/guild kick\|promote\|demote\|transfer` | **состав своей гильдии**, а не весь онлайн |
| `/guild invite` | игроки в сети |
| `/guild claim` | `remove` и регионы, **где вы владелец** |
| `/guild claim remove` | регионы, уже привязанные к вашей гильдии |
| `/guild admin bonus` | `list`, `grant`, `revoke` |
| `… bonus grant <вид>` | виды бонусов, затем величины под этот вид, затем сроки |
| `/guild admin friendlyfire` | `on`, `off` |
| `/guild help` | ровно столько страниц, сколько их у вас |
| `/party kick\|promote` | состав пати |
| `/party accept` | те, чьё приглашение ещё живо |
| `/party invite` | игроки в сети, **кроме тех, кто уже в пати** |

Чужие приваты в подсказках не светятся намеренно: привязать всё равно можно
только свой регион, а список чужих — это карта того, где на сервере есть что
взять.

**Имена из двух слов дополняются по слову за раз.** Bukkit режет команду по
пробелам, и «Ночные волки» одним токеном не дополнить: чем бы плагин ни
ответил, клиент подставит это вместо последнего слова. Поэтому набрал
«Ночные» — получил «волки», и только у тех имён, чьи предыдущие слова
совпали.

Разбор аргументов, общий для выполнения и подсказки, вынесен в
`core/ArgWords.java` и проверяется тестами. Причина та же, что и с HelpBook:
если команда считает «7d» сроком, а автодополнение — первым словом имени
гильдии, Tab предложит продолжение имени там, где его уже не будет. Разойтись
эти два места могут молча — подсказка ничего не выполняет.

## NPC — не игроки

Citizens спавнит своих NPC настоящими сущностями игрока и выбрасывает на
каждого `PlayerJoinEvent`. Без проверки ник и UUID торговца попадали бы в
справочник известных ников — и всплывали бы потом в автодополнении
админ-команд и в поиске игрока, вплоть до приглашения NPC в гильдию вместо
человека.

Проверяются метаданные `NPC`; зависимости на Citizens нет, на сервере без него
проверка всегда ложна. То же самое стоит в AurumAuth, где цена ошибки выше —
там NPC кикало бы по таймауту входа.

Хук для NPC-торговцев (`grantBonus` через `AurumGuildsApi`) это не затрагивает
вовсе: там чужой плагин зовёт API за игрока-человека, а не подключается сам.

## Проверка имени и тега

Запрещены `&` и `§` (иначе первый же игрок заведёт мерцающий тег, а следующий —
невидимый цветом фона), управляющие символы и пробелы по краям. Кириллица
разрешена: сервер русскоязычный, и заставлять писать «Драконы» латиницей
незачем. Уникальность считается без учёта регистра — «Драконы» и «драконы» для
любого читателя одна и та же гильдия.

## Язык плагина

`language: ru` в `config.yml` — `ru`, `en` или `pl`. Сами тексты лежат в папке
`lang/`, по файлу на язык, и правятся руками: формулировка применяется командой
`/guild admin reload`, пересобирать плагин не нужно. Ради этого всё и
затевалось — раньше каждая реплика жила в Java, и поправить запятую значило
пересобрать jar и перезалить его на живой сервер.

**Язык один на сервер, а не на игрока.** Так устроены все плагины Bukkit: чат
гильдии один на всех, сайдбар тоже. Выбирать язык на каждого значило бы
обещать то, чего протокол не даёт.

**Все три файла распаковываются сразу**, а не только выбранный, и при
обновлении плагина **не перезаписываются**: иначе стёрлись бы ровно те правки,
ради которых файлы и заведены. Недостающие после обновления ключи берутся из
встроенного русского — новые сообщения появляются сами, старые остаются
какими были.

**Подстановки в фигурных скобках оставлять обязательно.** `{player}`,
`{guild}`, `{max}` заполняются при показе; незаполненная подстановка остаётся в
чате как есть — так опечатку в файле видно сразу, а не «пропало слово».

### Имена ключей общие с панелью

`mc.rank.leader`, `mc.bonus.blockDrops` и остальные из раздела `mc:` — те же
имена, что в словаре панели. Плагин подставляет их на языке сервера, панель —
на языке того, кто смотрит. **Одно и то же имя ключа обязано означать одно и то
же слово по обе стороны**; добавить бонус значит дописать строку в двух местах,
а не заводить вторую таблицу соответствий.

### Ключ, а не фраза, — и почему их два вида

Правила гильдий живут в `core`, где нет ни конфига, ни игрока, поэтому наружу
оттуда уезжает `GuildActionResult` с ключом. Подстановок к нему **две карты**, и
это не избыточность: в `values` лежит то, что переводить нельзя (ник, имя
гильдии, сумма), в `keyKeys` — то, что само является ключом словаря (ранг, вид
бонуса, кому доступен банк). Разница видна на «{player} теперь {rank}»: ник
останется ником на любом языке, а «офицер» обязан стать «officer». Сложи их в
одну карту — и отличить одно от другого при выводе будет нечем.

Чужому плагину (например, торговцу-NPC, который покупает гильдии бонусы)
показывать `messageKey()` нельзя — это `guild.bonus.granted`, а не фраза.
Готовый текст на языке сервера отдаёт `AurumGuildsApi.render(result)`.

### Что остаётся русским намеренно

**Журнал сервера.** Его читает администратор в консоли, вперемешку с
сообщениями Paper и других плагинов. Смешивать там языки хуже, чем оставить
один: по логу ищут причину аварии, а не читают его как текст.

**Слова самих команд.** `deposit`, `confirm`, `выгнать` — это ввод, а не
сообщение. Английские работают на любом сервере, русские остались ради тех, кто
их уже выучил, а переводить их на польский значило бы сломать подсказку из
чужого гайда. По той же причине не переводятся имена видов бонусов
(`miningspeed` и прочие): их набирают, а не читают.

**Множитель «×1.5».** Это число, а не слово.

### Что берётся не из словаря, а у Java

**Дата создания гильдии.** `/guild info` показывает её в формате языка сервера:
«6 сент. 2026», «Sep 6, 2026», «6 wrz 2026». Шаблоном её задавать нельзя —
«06.09.2026» для англоязычного читателя это 9 июня, и разбираться, где день, а
где месяц, он не обязан.

**Единицы времени — сокращениями:** «2 ч 30 мин», «2 h 30 min». Полные слова
пришлось бы склонять по числу («2 godziny», «5 godzin»), а сокращения не
склоняются ни в одном из трёх языков.

### Что проверяется тестом

`LanguageFilesTest` в модуле paper читает файлы snakeyaml — тем же разбором,
что и внутри сервера, но без Bukkit, — и сверяет три вещи: во всех языках один
и тот же набор ключей, подстановки в переводе те же, что в русском, и каждый
ключ, который просит код (в том числе из `core`), в файле есть. Последнее ловит
опечатку в имени: она не падает и не подсвечивается типами — `Messages` честно
вернёт сам ключ, и в чат уедет «guild.err.notInGuidl».

### Что где: выключатели в config.yml, слова в lang/

Граница проходит по природе настройки, а не по важности. «Включён ли банк»,
«как часто обновлять сайдбар», «сколько живёт приглашение» — настройки сервера,
и они остаются в `config.yml`. Сами формулировки — в `lang/`.

## Панель

Вкладка «Гильдии» на экране сервера: список с поиском, карточка с полным
составом и рангами, баланс общака (если Vault есть), а для тех, у кого есть
право `minecraft.guilds.manage`, — принудительный роспуск, передача лидерства,
исключение участника и **выдача бонусов**: вид из списка, величина и срок
(навсегда, час, сутки, неделя, месяц). В карточке игрока показывается его
гильдия и ранг.

Величина, показанная после выдачи, — та, что действует на самом деле: плагин
подрезает её до потолка вида, и панель перечитывает список, а не рисует то, что
попросила.

Каждое действие попадает и в журнал панели, и в лог игрового сервера — там оно
подписано ником сотрудника, а не его идентификатором в панели: строчку в
консоли читает администратор, у которого панели под рукой может и не быть.

## Сборка

```bash
./gradlew build          # нужен JDK 25 для модуля paper
./gradlew :core:test     # логика — любым JDK 21+
```

Готовый `AurumGuilds-0.4.0.jar` кладётся в `plugins/`. Зависимости (HikariCP,
драйвер MariaDB) уже внутри. API AurumCore лежит в `local-repo/` и внутрь jar
не попадает: зависимость `compileOnly`, классы приходят от плагина AurumCore.

# Release 0.4.0: guild bank on AurumCore accounts

The guild bank moves to a real ledger account, `GUILD:<id>`. Deposits and
withdrawals become a single atomic transfer; `bank_balance` in the guilds
database becomes a mirror refreshed from the ledger after every operation.
Without AurumCore the bank keeps working through Vault exactly as before.

Existing balances are migrated once, automatically, on the first start with
AurumCore: a `MIGRATION` transfer from `SYSTEM_SOURCE:guild-bank-migration`
guarded both by a stable idempotency key and by a row in the new
`<prefix>_bank_migrated` table. Until a guild is migrated its bank answers
"please wait" instead of operating on the stale number. Review the policy
engine first — a server-wide `TAX` rule matching `GUILD_DEPOSIT` or
`MIGRATION` would silently shrink money that already existed.

**Behaviour change.** Disbanding a guild with a non-zero bank no longer makes
the money vanish, because on a ledger account it would instead be stranded on
an address no command can reach. The destination is configurable via
`bank.on-disband`: `leader` (default), `split`, `treasury` or `keep`. Set it to
`treasury` to send it to the global server treasury. Shares are frozen in two
small disband-plan tables before the first transfer, computed in integer cents,
and paid with stable keys. An interrupted disband resumes unpaid rows without
paying twice with AurumCore; Vault has no idempotency and cannot offer the same
crash guarantee. These tables are normally empty and are never read by HUD code.

No manual schema migration is required: the new tables are created on start.

# Release 0.3.0: social UI and guild switching

AurumUI 0.5.0 + AurumCompanion 0.5.0 expose player/leader/admin social menus.
The transport calls `aurumSocialSnapshot(Player, String)` and
`aurumSocialAction(Player, String, String, Map)`; the latter returns a future.
Database work never blocks the Minecraft payload handler. The provider checks
authentication and current permissions before calling the same services as commands.

Players may invite members of another guild. `/guild join [name]` first warns an
existing member and requires repeating acceptance within 30 seconds for the same
source and destination guild. UI acceptance shares this confirmation state.
The move is a single conditional SQL UPDATE; UUID is already the primary key.
On database failure membership and invitations remain unchanged. No schema migration
is required. A leader must transfer leadership or disband before switching.

The optional Fabric menu supports roster, settings, invitations, bank deposits,
withdrawals according to rank, and party management. Administrators need both
`aurumui.admin` and `aurumguilds.admin` for diagnostics, forced member/leader/disband
operations and bonus management. Install by replacing the old JAR and restarting.
